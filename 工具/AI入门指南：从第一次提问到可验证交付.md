# AI 入门指南：从第一次提问到可验证交付

## 这篇指南解决什么问题

很多人第一次使用 AI，会把重点放在“提示词够不够高级”。实际使用一段时间后，真正影响结果的通常是四件事：目标是否具体、输入是否可靠、权限是否合适、结果能否验收。

这篇指南根据一条真实的使用路径整理而成：用 AI 预习课程，逐步理解 C++；让 Agent 读取和维护本地知识库；做职业与项目调研；管理 PPT 制作资源；整理嵌入式实践；最后把可公开内容脱敏后发布到 GitHub。文章只保留可迁移的方法，不包含个人身份、内部路径、账号、学校内部资料或私有研究数据。

读完后，你应该能独立完成以下闭环：

```text
提出问题 → 限定范围 → 提供证据 → 让 AI 产出草稿
→ 自己验证 → 保存成果 → 复盘错误 → 继续迭代
```

如果一次对话结束后什么文件、练习、决策记录或测试结果都没有留下，这次使用的长期价值很低。聊天可以是入口，不能成为唯一的成果载体。

## 一、先理解 AI：它是什么，不能替你做什么

### 1. AI 的四种常见作用

| 作用 | AI 可以做什么 | 人必须检查什么 |
| --- | --- | --- |
| 生成 | 起草提纲、示例、代码、表格和表达方案 | 是否符合事实、语境和任务目标 |
| 转换 | 摘要、改写、分类、提取字段、翻译 | 是否遗漏条件、改变原意或混入臆测 |
| 推理辅助 | 比较选项、找矛盾、拆解问题、提出假设 | 推理链是否成立，证据是否足够 |
| 工具协作 | 读取文件、调用搜索、运行测试、修改文档 | 工具权限、变更范围、结果和副作用 |

AI 生成的句子很像结论，但语言流畅不等于事实正确。面对课程公式、代码运行结果、岗位要求、政策、价格、许可证和医学法律金融问题，都要把“回答”当作待检查对象。

### 2. 对话、资料增强和 Agent 不是一回事

可以把 AI 使用分成三层：

1. **普通对话**：你提问，模型根据当前上下文回答，适合解释概念、头脑整理和改写。
2. **资料增强工作流**：你提供教材、来源卡、代码或数据，模型根据这些材料整理，适合知识库、课程预习和报告编写。
3. **Agent 工作流**：模型能够按照指令循环调用工具，读取资料、修改文件、运行检查或提交变更，适合重复且有明确验收标准的工作。

Agent 的核心不是“更像人”，而是“能在工具和规则约束下完成多步工作”。它至少涉及模型、工具和指令三个部分；工具越强，权限风险也越高。OpenAI 的 Agent 指南也建议先从小范围、单 Agent 和真实任务验证开始，再根据失败证据增加复杂度。[OpenAI：构建 Agent 的实践指南](https://openai.com/business/guides-and-resources/a-practical-guide-to-building-ai-agents/)

### 3. 你需要区分五种错误

- **事实错误**：日期、定义、数字、规则或来源不存在。
- **推理错误**：前提看似正确，结论却没有由前提推出。
- **上下文错误**：模型忘了文件版本、任务范围或你前面写的限制。
- **执行错误**：路径错、命令失败、代码没有编译、文件没有真正写入。
- **状态错误**：模型依据的是旧文件、旧价格、旧岗位或旧的 Git 状态。

不同错误要用不同办法处理。查事实要回到来源，查推理要做反例和推导，查执行要看终端和文件，查状态要重新读取当前内容。继续追问“你确定吗”通常不能替代这些检查。

## 二、第一次使用：先写任务卡，再写提示词

### 1. 最小任务卡

每次让 AI 做稍微复杂的事前，先填六个字段：

```markdown
目标：我要解决什么问题？
输入：AI 可以读取哪些资料？
范围：只处理哪些文件、主题或时间段？
禁止：不能读取、不能修改、不能推断什么？
产物：最后必须留下什么文件、表格、代码或决定？
验收：我用什么证据判断它完成了？
```

例如，“帮我整理 AI”没有可执行边界。改写成：

```text
请根据我提供的课程预习笔记，整理一篇面向零基础学生的 AI 学习方法页。
只使用提供的材料和官方来源，不补写学校内部要求，不暴露个人信息。
文章必须包含：使用场景、输入、步骤、示例提示词、独立练习、验收标准和失败修正。
输出为 Markdown 文件，结尾列出来源和未验证事项。
```

第二种写法并不神秘，它只是提前回答了“做什么、根据什么、做到什么程度、哪里停止”。

### 2. 第一次对话的推荐顺序

不要一上来要求 AI 写最终稿，按下面顺序推进：

1. 让 AI 复述目标、范围、风险和验收标准。
2. 让 AI 列出它缺少的资料，而不是让它自行补齐。
3. 先产出结构、候选清单或问题列表。
4. 对关键事实逐项核验。
5. 再生成正文、代码或文件修改方案。
6. 让 AI 给出自检结果，人再做独立抽查。

这个顺序能减少一种常见浪费：AI 写了很多内容，最后才发现对象、路径、时间范围或资料权限都错了。

### 3. 提示词的最小模板

```text
你要完成的任务：{一句话目标}

可读取范围：{文件、网页、代码或我粘贴的材料}
可编辑范围：{允许修改的文件或目录}
禁止事项：{隐私、第三方原文、删除、外部发布、无来源推断}

交付物：{文件名、表格、代码、报告或回答格式}
验收方式：{运行测试、来源核对、链接检查、人工抽查或外部反馈}
停止条件：{资料缺失、权限不明、风险过高、验收失败时先提问}

开始前先复述：目标、范围、风险、计划和验收。
结束时给出：变更清单、验证结果、未解决问题和下一步。
```

提示词的价值不在于堆叠“你是世界顶级专家”等角色设定，而在于把下一步动作和停止条件写清楚。角色可以帮助调整表达风格，任务契约才真正约束行为。

## 三、把 AI 用于学习：解释不能替代练习

### 1. 课程预习的可执行流程

我实际采用过的课程预习流程是：

1. 输入公开课程大纲、教材版本、已学基础和预习时长。
2. 让 AI 建立章节依赖关系，不先生成长篇讲义。
3. 每章只提取四项：核心概念、典型题型、常见误区、待核验问题。
4. 回到教材或教师公开要求，核对定义、公式、例题条件和考核边界。
5. 不看 AI 完成一道题、一段推导或一段自己的解释。
6. 把错误按概念、条件、计算、表达和工具分类。
7. 只把已经核验的结构和错因写入正式笔记。

可直接复制的提示词：

```text
课程：{名称}
教材：{书名与版本}
我的基础：{已学内容}
可用时间：{每天或本周时长}

请根据下面的目录输出：
1. 章节先后依赖；
2. 每章一个可检查的学习目标；
3. 每章三个常见误区；
4. 必须回到教材核验的事实。

不要补充目录中不存在的课程要求，不要把猜测写成确定结论。
目录：{粘贴公开目录}
```

验收标准是：你能在不看 AI 的情况下解释一个概念、完成一个基础题或写出一个最小示例。只保存 AI 生成的讲义，不算完成学习。

### 2. C++ 学习中的正确用法

在 C++ 学习中，最容易出现的问题是 AI 给出“看起来能用”的完整答案，却没有解决“到底是谁和谁在运算”。更可靠的练习方式是要求它只解释一个动作，并提供可以运行的最小程序。

```text
我正在学习 {概念}，基础是 {基础}。
不要直接给完整项目或最终答案。
请按以下顺序：
1. 用一句话说明结论；
2. 标出每个变量当前保存的值；
3. 说明每一步是谁和谁在运算；
4. 给一个只演示该概念的完整最小程序；
5. 写出预期输出；
6. 给我一道相似但数字不同的题，先不要公布答案。
```

拿到代码后必须做三件事：自己预测输出、实际编译运行、解释输出为什么与预测一致或不一致。对指针、位运算、容器和递归尤其如此，因为语法正确不代表模型理解正确。

### 3. AI 学习的四轮循环

```text
第一轮：让 AI 解释
第二轮：让 AI 出题
第三轮：独立作答并让 AI 只批改
第四轮：把错因和边界写成自己的笔记
```

批改提示词要限制 AI 的行为：`只指出第一处错误，不直接重写整题；说明错误属于概念、条件、计算还是表达；等我修正后再继续。`

## 四、把 AI 用于资料与知识库：让聊天变成可检索资产

### 1. 五层结构

一个可维护的知识库至少要区分以下层：

| 层 | 作用 | 允许写什么 |
| --- | --- | --- |
| Source | 证据 | 原文摘录、来源、作者、日期、链接、证据状态 |
| Wiki | 理解 | 稳定概念、机制、规则、边界、来源 |
| Research | 探索 | 问题、假设、比较、未完成分析 |
| Outputs | 交付 | 报告、课程作业、图表、演示文稿、最终版本 |
| System | 规则 | 模板、索引、权限、日志、检查脚本 |

这不是形式主义。把原始材料、个人推测、正式结论和最终交付混在一页里，几周后就无法判断哪句话有来源、哪句话已经过时。

### 2. 四个基本动作

**入库（ingest）**：先保存来源，补齐来源类型、作者、日期、URL 或本地文件位置，不急着生成大量总结。

**编译（compile）**：从来源提炼一篇可复用知识卡。每页只解决一个主要问题，写清定义、机制、动作、适用条件、失效条件和验证方法。

**查询（query）**：先查知识地图，再查 Wiki，再回到 Source。回答时区分事实、推论、建议和未验证假设。

**维护（maintenance）**：检查孤立页、断链、重复主题、过期快照、缺来源结论和没有验收标准的空壳笔记。

### 3. 资料整理提示词

```text
请处理下面这份资料，但不要直接把它写成确定事实。

输出四部分：
1. 来源信息：作者、日期、原始 URL 或文件位置；
2. 可确认事实：逐条列出并保留定位信息；
3. 观点、推论和待核验内容：分开标注；
4. 是否值得编译成长期笔记：说明理由和缺口。

禁止：补写来源中不存在的数字、规则、个人经历和结论。
```

### 4. 笔记质量门槛

一篇通用方法页至少回答六个问题：

- 何时使用？
- 需要什么输入？
- 按什么步骤执行？
- 最后留下什么产物？
- 如何验收？
- 什么情况下失效或必须复核？

缺少步骤的文章是观点，缺少验收的文章是建议，缺少边界的文章容易误导。写作时先写交付物和验收，再倒推步骤，比先写一段漂亮的引言更可靠。

## 五、把 AI 用于调研：来源、时效和结论强度必须匹配

### 1. 哪些内容必须查当前来源

岗位、公司、薪资、城市、招生政策、比赛规则、软件版本、价格、许可证和平台功能都可能变化。它们必须记录采集日期、原始链接和行动前复核要求。

职业调研可以保留公司、岗位、薪资和城市这些公开字段，但要明确它们只是岗位快照，不是个人承诺，也不是完整市场样本。一个可复查的记录至少包含：

```text
采集日期
公司与岗位
城市
薪资区间及口径
学历和技能要求
原始链接
证据等级
仍需复核的事项
```

### 2. 四种结论不要混写

| 类型 | 写法 | 例子 |
| --- | --- | --- |
| 事实 | “来源页面写明……” | 某岗位页面列出 C++ 和 Python |
| 推论 | “根据多个样本，我推断……” | 两类岗位都要求把代码跑通，因此验证能力重要 |
| 建议 | “对学习安排可采取……” | 先做一个可运行的信号处理小项目 |
| 假设 | “尚未验证，待测试……” | 某方向可能更适合当前基础 |

把四种句式混成“行业都这样”“学会就能就业”，就会把样本、推测和承诺混为一谈。

### 3. 让 AI 做研究助理，不让它替你宣布结论

让 AI 做这些工作很合适：抽取岗位字段、去重、比较要求、找冲突、生成核验表、提出下一步搜索词。让 AI 直接宣布“哪个职业最适合你”“这个方向一定有前景”，则需要谨慎，因为这类结论依赖个人约束和未来信息。

研究输出的最低验收标准：每个关键结论都能回到来源；来源冲突被单独列出；样本数量和采集时间写明；未验证事项没有伪装成结论。

## 六、把 AI 用成 Agent：权限越大，验收越严格

### 1. 什么时候值得使用 Agent

至少满足两项再考虑 Agent：

- 工作会重复发生；
- 输出格式比较固定；
- 需要跨文件或跨工具；
- 能写出独立验收标准；
- 失败后可以回退或交给人处理。

一次性的开放讨论，不需要把权限升级成 Agent。模型、工具和指令三者共同决定风险，复杂架构不能弥补模糊目标。

### 2. 权限分级

```text
第 1 级：只读，列出候选、风险和方案
第 2 级：写入本地草稿，可回退
第 3 级：运行测试、生成索引、制作报告
第 4 级：提交 Git，仍需人工查看 diff
第 5 级：外部发布、发送消息、花钱或不可逆操作，必须人工确认
```

在真实的公开库整理中，可靠顺序是：读取私有来源 → 选取候选 → 建立暂存镜像 → 脱敏改写 → 链接和敏感信息检查 → 查看 diff → 本地提交 → 推送 → 回读远端状态。不能因为 Agent 能访问某目录，就让它把整个目录复制到公开仓库。

### 3. Agent 任务契约示例

```markdown
# 任务契约

## 目标
从指定来源中整理一篇公开版方法页。

## 可读取
- 已授权的来源目录
- 公开官方网页

## 可编辑
- 暂存目录中的指定 Markdown 文件

## 禁止
- 不读取或发布账号、密钥、个人联系方式和内部资料
- 不复制第三方原文、压缩包、生成物和未授权图片
- 不删除原始来源
- 不执行外部发布，除非我单独确认

## 交付物
- 公开版 Markdown
- 来源与边界说明
- 变更清单
- 验证报告

## 验收
- 本地链接无断链
- 没有个人信息和内部路径
- 每个事实性结论有来源或被标为待核验
- Git diff 可读且只包含指定文件
```

### 4. 工具输出不等于任务完成

Agent 说“已写入”时，要实际读取文件；说“已提交”时，要看 Git 日志；说“测试通过”时，要确认运行的是当前源文件；说“已发布”时，要核对远端提交号。任何一步缺少证据，都只能写成“待确认”。

## 七、把 AI 用于代码和文件：先看当前状态，再动手

### 1. 文件任务的标准顺序

```text
确认工作区 → 读取相关文件 → 搜索重复内容
→ 说明最小修改 → 修改 → 查看 diff
→ 运行检查 → 再决定是否提交
```

在 Windows 环境中，路径和编码本身就是任务的一部分。不要把相似的目录名、子知识库和 Git 根目录混为一谈；先确认当前目录，再用精确路径读取。

### 2. C++ 或脚本出现奇怪结果时

先检查：

1. 源文件最后修改时间；
2. 可执行文件最后修改时间；
3. 是否重新编译；
4. 实际运行的路径；
5. 输入样例是否与题目一致；
6. 输出格式是否要求特殊字符。

“程序能运行”只说明某个二进制启动了，不能说明它对应当前源代码。一个旧的可执行文件可能让你误判已经修复问题。

### 3. 最小验证命令

```powershell
git status --short
git diff --check
```

代码还需要真正编译和运行；文档还需要检查链接、来源和敏感信息；数据还需要检查行数、字段和缺失值。验证命令必须对应交付物，不能只执行一个看似通用的命令。

### 4. 修改边界

先修一个具体错误，再考虑重构。不要让 AI 顺手重命名一批文件、重排整个目录或覆盖原始来源。原始材料和编译结果应分开保存，便于回退、比较和重新编译。

## 八、把 AI 用于 PPT 和视觉工作：先有结论，再找装饰

PPTmaker 的实际整理经验说明，演示文稿最容易出现两类问题：先找模板再硬塞内容；素材看起来免费却没有记录来源和许可证。

### 一页 PPT 的生产闭环

1. 用一句话写页面结论。
2. 列出支撑它的 3 至 5 个证据。
3. 决定证据用文字、表格、流程图还是数据图表达。
4. 再选择图标、照片、插画和颜色。
5. 把外来素材写入使用记录，包含 URL、许可证、作者和下载日期。
6. 导出 PDF，在 100% 和全屏投影场景下验收。

页面验收至少包括：标题能否独立表达结论，正文是否可读，数字和单位是否有来源，外来素材是否能定位，导出后字体和分页是否稳定。

公开仓库可以发布制作规范、来源索引、许可证记录模板和核验脚本；不应把具体课件、个人项目资料、来源不明模板和第三方大资源包顺手打包公开。许可证允许使用，不等于任何场景都允许再分发。

## 九、把 AI 用于开源：公开前先做边界审计

### 1. 四类内容的处理方式

| 内容 | 公开处理 |
| --- | --- |
| 通用方法 | 改写为脱离个人、学校和年份也成立的步骤 |
| 个人经历 | 提取可迁移做法，删除姓名、账号、路径和可定位细节 |
| 时效快照 | 保留公开字段、日期、来源链接和复核提醒 |
| 私有材料 | 不公开；需要时只总结方法，不复制原文 |

### 2. 发布前检查表

- 是否出现姓名、邮箱、电话、账号、令牌或个人地址？
- 是否出现本地绝对路径、内部服务器、学校内部流程或未公开通知？
- 是否把个人经历写成普遍规律？
- 是否直接复制第三方文章、截图、课程资料、模板或资源包？
- 是否为岗位、价格、规则和许可证写了日期与原始链接？
- 是否保留了必要的许可证和署名要求？
- 是否只提交了本次确认的文件？
- 是否查看了 `git diff`、`git diff --check` 和提交后的远端状态？

公开仓库的密钥问题要按“已经泄露”处理，不能只把当前文件删除就认为安全，因为 Git 历史仍可能保留旧内容。GitHub 的 Secret Scanning 和 Push Protection 可以作为额外防线，但不能替代发布前的人工审计。[GitHub：Secret scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning) [GitHub：安全功能](https://docs.github.com/en/code-security/getting-started/github-security-features)

## 十、六个可直接复制的任务模板

### 模板 A：概念学习

```text
请教我 {概念}。我的基础是 {基础}。
先给一句话结论，再解释机制，明确每一步参与运算的对象。
给一个最小可运行示例和预期输出，再给一道不公布答案的练习。
指出一个常见误区、一个失效边界和我需要自己核验的内容。
```

### 模板 B：资料入库

```text
请把这份资料整理为 Source 卡片。
保留来源、作者、日期、URL、原文事实和证据状态。
把观点、推论、待核验内容分开，不生成没有来源的结论。
最后说明它是否适合编译为长期知识页，以及缺少什么证据。
```

### 模板 C：代码排错

```text
请先读取当前源文件和代表性输入，不要直接重写。
指出实际错误、触发条件和最小修正。
给出修改后的 diff、编译命令、测试输入、预期输出和边界样例。
如果无法运行，请明确标记为未验证，不要说“应该可以”。
```

### 模板 D：时效调研

```text
请调研 {主题}，只使用可定位的公开来源。
每条结论标注来源、发布日期或采集日期、证据等级和复核要求。
分开写事实、推论、建议和未验证假设。
不要把搜索摘要、单个样本或过期页面写成普遍规律。
```

### 模板 E：知识库维护

```text
请先检查当前知识库结构和最近日志。
只处理 {指定范围}，不修改来源层原文，不删除文件。
先列出候选问题，再执行最小修改。
完成后检查本地链接、重复主题、敏感信息、来源和 diff。
输出变更文件、验证结果、剩余问题和下一步。
```

### 模板 F：公开发布

```text
请将指定内容编译为公开版。
删除个人信息、账号、内部路径、学校内部细节、未公开资料和第三方原文。
保留通用方法、公开事实、来源链接、日期、许可证和复核边界。
只修改暂存目录中的指定文件。
发布前执行链接、脱敏、版权和 diff 检查；没有人工确认不要推送。
```

## 十一、七天入门练习计划

每天留下一份可以回看的产物，不追求一次学会所有工具。

| 天数 | 练习 | 产物 | 验收 |
| --- | --- | --- | --- |
| 第 1 天 | 用最小任务卡问一个熟悉问题 | 一张任务卡和一份回答 | 能指出目标、输入和验收 |
| 第 2 天 | 让 AI 解释一个陌生概念 | 一页解释和三个核验问题 | 能回到教材或官方来源 |
| 第 3 天 | 做一次独立练习 | 题目、答案、错因记录 | 不看 AI 能完成基础题 |
| 第 4 天 | 建一张 Source 卡片 | 来源卡和待核验清单 | 事实与观点分开 |
| 第 5 天 | 让 AI 检查一个小程序或表格 | diff、测试输入和输出 | 结果经过真实运行 |
| 第 6 天 | 设计一个只读 Agent 任务 | 任务契约和权限表 | 能写出停止条件 |
| 第 7 天 | 发布一页公开版方法 | Markdown、来源和审计记录 | 链接、隐私和版权检查通过 |

第七天之后再考虑自动写文件、批量整理或外部发布。先把一个小闭环做可靠，能力会比收集大量提示词增长得更快。

## 十二、最常见的失败及修正

| 失败表现 | 根因 | 修正动作 |
| --- | --- | --- |
| AI 写了一大段空话 | 目标和产物不明确 | 先写任务卡，要求表格、步骤和验收 |
| 解释很流畅但事实错误 | 把语言流畅当成证据 | 回到教材、官方页面或可运行测试 |
| 一次粘贴整个资料库 | 上下文和隐私边界失控 | 先列候选文件，按需提供最小资料 |
| Agent 改了不该改的文件 | 编辑范围没有写清 | 设置可编辑目录，先只读再写入 |
| 代码输出像对但跑不通 | 没有编译、输入和预期输出 | 要求最小程序并实际运行 |
| 运行结果和当前代码不一致 | 执行了旧二进制或旧文件 | 比较源文件和产物时间，重新构建 |
| 研究结论过度确定 | 样本、日期和证据等级缺失 | 分开事实、推论、建议、假设 |
| 聊天结束后找不到成果 | 没有保存交付物 | 每次对话必须留下文件、记录或练习 |
| 公开库混入个人或内部资料 | 只检查正文，没检查路径和历史 | 发布前扫描正文、文件名、绝对路径和 Git 历史 |
| PPT 看起来漂亮但不能交付 | 先装饰，后补结论；素材无记录 | 先结论和证据，再做版式和授权记录 |

## 十三、最终操作清单

在提交一个复杂 AI 任务前，逐项回答：

1. 我到底要解决哪个具体问题？
2. AI 可以读取哪些资料，不能读取哪些资料？
3. 哪些结论必须回到原始来源？
4. 最终产物是什么，放在哪里？
5. 我如何独立验收，而不是只看 AI 自评？
6. 这次任务需要普通对话、资料工作流还是 Agent？
7. 工具权限是否足够小，失败后能否回退？
8. 是否记录了日期、版本、来源和未验证事项？
9. 是否把个人、内部和第三方受限内容排除在外？
10. 完成后是否留下了可复查的文件、测试、日志或决策记录？

AI 入门的核心不是学会一套固定咒语，而是形成一种工作纪律：把目标写清，把证据分层，把权限关小，把结果存下来，把错误暴露出来。模型会变，平台会变，工具会变，这套纪律仍然适用。
