## 二、SPL 对照：库函数的两种参数风格

标准外设库里反复出现这两种签名，看懂它们就看懂了库的用法。

### 风格一：传入一个结构体的地址，由函数填值

```c
GPIO_InitTypeDef gpio;
gpio.GPIO_Pin   = GPIO_Pin_5;
gpio.GPIO_Mode  = GPIO_Mode_Out_PP;
gpio.GPIO_Speed = GPIO_Speed_50MHz;
GPIO_Init(GPIOA, &gpio);        /* 传地址：函数要读这个结构体 */
```

调用方负责准备结构体，库函数只读不写（参数常带 `const`）。这种风格的好处是参数多时不用写一长串。

### 风格二：传数组必带长度

```c
void uart_send(const uint8_t *data, size_t len);   /* 自己写的驱动应当这样签名 */
```

绝对不要写成：

```c
void uart_send(const uint8_t *data);   /* 函数里无法知道有多少字节 */
```

这是 K06 的核心：**数组传进来只剩地址，长度必须跟着一起传**。库里若出现不带长度的版本，通常是因为长度被约定成固定值（比如固定发 8 字节）。

### 风格三：返回状态，结果用指针带出

```c
FlagStatus s = GPIO_ReadOutputDataBit(GPIOA, GPIO_Pin_5);
```

返回值表达结果，参数表达对象。自己写驱动时沿用这个约定：

```c
int sensor_read(uint16_t *out_value)   /* 返回 0 表示成功，非 0 是错误码 */
{
    if (out_value == NULL) return -1;
    /* … */
    *out_value = v;
    return 0;
}
```

## 三、为什么嵌入式里更要小心参数

- 传错地址会改到**寄存器**，不是普通变量——后果是硬件行为异常，不是程序报错
- 数组越界会踩到相邻的外设数据或栈，现象是偶发死机，很难定位
- `const` 不仅能防误改，还能让编译器把只读数据放进 Flash，省 RAM

## 四、把本知识点带回 PC 的做法

写驱动函数时先在 PC 上用普通变量模拟：

```c
uint16_t fake_reg = 0;
int r = sensor_read(&fake_reg);   /* 用假变量验证参数与返回值逻辑 */
```

把「参数约定」调对之后，再换成真实寄存器地址，出错时只剩硬件一层要查。
