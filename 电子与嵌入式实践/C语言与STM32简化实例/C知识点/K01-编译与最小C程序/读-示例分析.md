# K01 读：exercism 的 makefile 与最小骨架

读的对象：`exercism-c/c-main/exercises/practice/hello-world/`（来源 exercism/c，MIT）。
原则：只引用位置与必要片段，分析由本人写；完整原文仍在原目录，本库不复制整篇。

## 这个例子为什么值得读

它把「一个最小 C 工程该有什么」压缩到了 5 个文件：头文件、源文件、测试文件、测试框架、makefile。读懂它，后面 84 题的目录结构都不用再学一遍。

## 一、`hello_world.h`：头文件只放声明

（原示例代码未随公开版复制；此处保留分析结论。）

- `ifndef/define/endif` 是 include guard：同一个头文件被包含两次时，第二次因宏已定义而整段跳过，避免重复声明报错
- 头里只有**声明**（函数长什么样），没有**定义**（函数体在函数体在 `.c` 里）。这是多文件 C 工程的基本分工
- `const char *` 表示「指向只读字符的指针」，这里指向字符串字面量

## 二、`hello_world.c`：故意写错的骨架

（原示例代码未随公开版复制；此处保留分析结论。）

这是**故意**的：测试要求返回 `"Hello, World!"`，骨架先给一个错的值，让 `make test` 必然失败。

这个设计本身就是教学方法：先看到红，再改到绿。不要一上来就去翻 `.meta/example.c`（官方参考解），那样只是抄，不是练。

## 三、`test_hello_world.c`：测试长什么样

（原示例代码未随公开版复制；此处保留分析结论。）

- `setUp` / `tearDown` 是每个测试前后跑的钩子，这里为空
- `main` 在测试文件里，不在被测代码里 —— 因为可执行程序的入口只有一个，被测试驱动占用了
- `TEST_ASSERT_EQUAL_STRING` 来自 unity 框架（`test-framework/unity.c`），比较的是字符串内容，不是指针地址

## 四、`makefile`：这套开关值得照抄

（原示例代码未随公开版复制；此处保留分析结论。）

逐条：

| 开关 | 作用 | 为什么有用 |
| --- | --- | --- |
| `-std=c99` | 指定语言标准 | 固定方言，避免编译器默认版本变化导致行为漂移 |
| `-g` | 带调试信息 | 出问题时能定位到行 |
| `-Wall -Wextra` | 打开主要警告 | 大多数低级错误在编译期就暴露 |
| `-pedantic` | 严格按标准检查 | 挡住 GNU 扩展，保证可移植 |
| `-Werror` | **警告即错误** | 逼你把警告清干净，而不是攒着 |
| `-Wmissing-declarations` | 函数缺声明就报 | 防止忘记写头文件声明 |
| `-DUNITY_SUPPORT_64` | 给测试框架用的宏 | 支持 64 位断言 |

`-Werror` 是这套配置里最有教学价值的一条：它把「能过编译」的标准从「没语法错」抬到「没有可疑写法」。

## 五、两个 make 目标

（原示例代码未随公开版复制；此处保留分析结论。）

- `test`：先编译出 `tests.out`（把 unity 框架、所有 `.c` 一起编），再运行
- `memcheck`：额外加 `-fsanitize=address`（ASAN），跑同一批测试但检查内存错误（越界、use-after-free、内存泄漏）

`memcheck` 值得单独记住：C 里很多错误「跑起来像是对的」，只有 ASAN 能当场抓出来。

## 与本知识点的关系

`test` 目标那条命令就是 K01 四步里「编译 + 链接」的一次性写法：`$(CC) $(CFLAGS) unity.c ./*.c -o tests.out` —— 多个 `.c` 一起喂给编译器，链接阶段拼成一个可执行文件。
