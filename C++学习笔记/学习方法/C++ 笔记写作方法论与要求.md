# C++ 笔记写作方法论与要求

## 目标

笔记的用途不是复制教材，而是降低下一次解决同类问题的成本。

一篇合格的 C++ 笔记，应当回答五个问题：

1. 这是什么？
2. 它解决什么问题？
3. 编译器或运行时为什么会这样工作？
4. 正确写法是什么？
5. 在什么条件下会失效、变慢或出错？

如果只能回答第一个问题，这更接近术语摘录，不是可用知识。

## 一篇笔记只处理一个核心问题

范围过大的标题通常意味着内容不可复用。

| 不推荐标题 | 更好的拆分 |
| --- | --- |
| 指针 | NULL 与 nullptr：空指针的现代写法、delete：销毁动态对象并归还内存、指针所有权、悬空指针 |
| 输入输出 | std-endl：换行与刷新输出缓冲区、流缓冲、文件流、格式化输出 |
| C++ 面向对象 | 构造函数、析构函数、虚函数、对象切片、继承访问控制 |

判断标准：能否用一句话说出“这篇笔记要解决的唯一问题”。说不出来，就继续拆分。

```markdown
# 标题

## 一句话结论
先给可执行判断。

## 它解决什么问题
解释使用场景，而非只下定义。

## 工作机制
说明编译期、运行期、对象生命周期或资源所有权等关键机制。

## 最小示例
给出短小、可独立理解的代码。

## 常见错误与边界
写出错误示例、后果和例外条件。

## 使用规则
压缩为可执行的几条规则。

## 关联

## 来源
标准条款、官方文档或可核验资料。
```

这是一套默认模板，不是死板格式。只有在某一节能提高理解或复用性时才保留它。

## 写作步骤

### 1. 从真实问题开始

不要先问“我要记哪些知识点”，先记录你遇到的具体困惑。

例如：

- 为什么 `std::endl` 让程序变慢？
- `NULL` 和 `nullptr` 能否混用？
- `delete` 之后指针为什么还能打印一个地址？

真实问题能暴露概念的边界，也决定示例该写什么。

### 2. 先给结论，再补推理

读笔记时最先需要的是决策，不是铺垫。

坏写法：先抄一段冗长定义，最后才说应使用 `nullptr`。

好写法：开头直接写“C++11 及以后用 `nullptr` 表示空指针”，随后解释其类型和重载差异。

### 3. 用最小示例验证一个规则

每段代码只证明一个结论。示例应尽可能短，并包含必要上下文。

```cpp
int* p = nullptr;
if (p == nullptr) {
    // p 不指向对象
}
```

不应在解释空指针时同时引入类继承、模板、文件 I/O 和异常处理。额外复杂度会遮住真正的规则。

### 4. 记录反例与失败方式

C++ 的风险常常来自“代码能编译，却不代表正确”。每篇涉及资源、指针、类型转换或并发的笔记，至少记录一个失败案例。

```cpp
int value = 1;
int* p = &value;
// delete p; // 未定义行为
```

需要写清：错误前提、可能后果、正确替代方案。

### 5. 标明版本和证据等级

语言规则会随 C++ 标准演进，库行为也可能受实现影响。笔记应区分：

| 内容类型 | 写法要求 |
| --- | --- |
| 语言规则 | 标注适用标准，例如“C++11 及以后”；优先引用标准条款 |
| 标准库接口 | 标注头文件、接口名和来源 |
| 编译器行为 | 标注编译器、版本、编译选项和复现实验 |
| 个人经验 | 标注为经验或待验证结论，不能伪装成语言规则 |

## 代码注释要求

代码示例中，除 `#include`、花括号、单纯的类型声明等明显基础语法外，每个关键代码行都应添加行尾或单独一行的中文注释。注释至少说明：

1. 这一行处理谁。
2. 这一行改变了什么。
3. 这一行为什么这样写。

示例：

```cpp
int k;                         // 保存要比较的列号
std::cin >> k;                 // 读取列号，列号从 0 开始
std::sort(arr.begin(), arr.end(), // 对所有行重新排列
    [k](const Row& a, const Row& b) { // 比较两行的第 k 列
        return a[k] < b[k];     // 第 k 列较小的行排在前面
    });
```

注释不重复解释 `int`、`;` 等已经掌握的基础语法，重点解释数据流、边界和算法意图。

## 质量要求

一篇笔记完成前，检查以下事项：

- [ ] 标题能准确说明问题，且范围不过大。
- [ ] 开头有一句可执行的结论。
- [ ] 有一个最小示例。
- [ ] 解释了关键机制，而不只给定义。
- [ ] 写明至少一个误区、反例或适用边界。
- [ ] 涉及标准规则时，标注 C++ 版本与来源。
- [ ] 链接到已有相关笔记，避免知识孤岛。
- [ ] 删除无助于理解的废话、重复定义和未验证断言。

## 复盘要求

当一个问题被实际代码触发后，回到对应笔记，补充三类信息：

1. 触发场景：哪段代码、什么报错或异常行为。
2. 原因：违反了哪条规则，或遗漏了什么前提。
3. 修正：最终如何改，以及是否有更稳妥的设计。

持续积累后，笔记会从“概念说明”演化为个人的排错手册。
