# 仿真端点记录：主机模拟、端点表与硬件证据

这张记录卡用于主机仿真、网络模拟器或设备联调。它解决一个常见混淆：程序在电脑上跑通，只能说明指定的软件、模型和虚拟端点能够协作，不能直接说明真实板卡、串口电平、射频链路、传感器和失效保护已经通过验证。

本页沿用 ArduPilot 官方 SITL 文档中的端点记录思路，示例端口只作为文档记录，不代表当前版本、当前系统或本次整理已经运行成功。

## 1. 先把证据分成三层

| 层级 | 能回答的问题 | 需要留下的材料 |
| --- | --- | --- |
| 官方或项目文档 | 软件如何启动、端点如何连接、某个参数怎样解释 | 原始链接、访问日期、适用版本 |
| 主机仿真运行记录 | 指定版本、模型、命令和端点是否在仿真环境中连通 | 启动命令、版本、模型、标准输出、日志、抓包或消息统计 |
| 真实设备记录 | 板卡与真实外设是否按预期工作 | 板卡型号与修订版、固件、串口或网络介质、供电、传感器、射频环境、故障现象 |

写结论时把层级写进句子里。例如：

- “官方文档说明首个实例的端点角色如下。”
- “某次主机仿真记录显示指定模型启动并产生消息。”
- “真实设备记录显示某块板子的串口电平和传感器行为符合预期。”

不要把第一层写成第二层，也不要把第二层写成第三层。

## 2. 端点表先于启动命令

启动前先填表。未知项写“待确认”，不要用猜测补全。

| 字段 | 填写内容 |
| --- | --- |
| 实例编号 | 0、1 或项目自定义编号 |
| 软件与版本 | 项目、分支或发行版版本 |
| 仿真模型 | 载具、拓扑、传感器或业务模型 |
| 端点角色 | 控制程序、地面站、伴随计算机、外部模拟器、日志端 |
| 传输方式 | TCP、UDP、串口模拟或其他协议 |
| 本地动作 | bind、listen、connect 或由工具自动分配 |
| 对端地址 | 用脱敏后的主机名或文档占位符 |
| 端口 | 端口号、来源和是否由实例编号计算 |
| 配置来源 | 官方文档、命令行、配置文件或运行输出 |
| 日志位置 | 标准输出、应用日志、抓包或消息统计 |
| 结果状态 | 未运行、启动、已连接、异常、已结束 |

端点表的目的不是把配置抄得越多越好，而是让另一个人能回答“谁在等谁、谁连谁、哪一个端口属于哪一个实例”。

## 3. ArduPilot SITL 的文档示例怎样记录

ArduPilot 官方文档将 SITL 描述为在没有真实硬件时运行自动驾驶软件的方式，传感器数据由飞行动力学模型或外部模拟器提供。文档给出的首个实例端点示例包括：

| 角色 | 官方文档示例 |
| --- | --- |
| SERIAL0 | TCP 5760 |
| RC 输入 | UDP 5501 |
| 地面站的 MAVLink | UDP 14550 |
| SERIAL1 | TCP 5762 |
| SERIAL2 | TCP 5763 |

这些值必须和“首个实例、当前文档版本”一起记录。后续实例使用 -I n 时，官方文档说明端口按实例编号增加偏移，且多数端口可以在命令行中改写。因此不能把首个实例的表格复制给第二个实例；应重新填实例编号、实际端口和日志位置。

可记录的启动形状如下，尖括号内容需要按目标项目和版本替换：

~~~sh
sim_vehicle.py -v <vehicle> -I <instance>
~~~

这只是命令形状和记录模板。本轮没有启动 SITL，也没有重新确认端口行为。

## 4. 一次可复查的仿真流程

### 第一步：固定问题边界

先写清楚本次只回答什么：

- 模型能否启动；
- 控制程序与地面站能否建立消息通道；
- 多实例端点是否互不冲突；
- 某个参数变化是否影响指定的虚拟输出；
- 外部模拟器是否按预期接入。

不要用“仿真通过”代替这些具体问题。

### 第二步：保存版本和输入

记录软件版本、分支或构建标识，模型名称，启动参数，外部模拟器版本，以及端点表。参数中若包含本机绝对路径、账号、令牌或内部地址，发布前改为占位符。

### 第三步：启动后只看与问题有关的证据

按问题选择材料：

- 启动问题：标准输出、退出码和启动日志；
- 连接问题：监听端点、连接端点、协议方向和消息计数；
- 多实例问题：实例编号、端口表和每个实例的独立日志；
- 参数问题：参数快照、输入条件、输出指标和时间范围；
- 网络问题：必要时保留脱敏后的抓包摘要，不公开内部地址和设备标识。

### 第四步：把结果写成状态

每个结果至少带上：

~~~text
问题：
软件与版本：
模型：
实例：
输入条件：
端点：
证据文件：
观察到的结果：
仍未知：
~~~

“未运行”“已启动但未连接”“连接成功”“输出异常”是不同状态，不能合并成一个“通过”。

## 5. 仿真结果的边界

主机仿真通常能够支持这些判断：

- 指定软件版本可以在给定模型和输入条件下启动；
- 虚拟控制程序、地面站、外部模拟器或伴随进程的端点关系成立；
- 某些软件逻辑、消息流和参数处理可以在主机环境中复现。

它不能单独证明：

- 真实串口的电压、电平、线序和波特率；
- 真实板卡的供电、时钟、Flash、驱动和启动过程；
- 无线链路的覆盖、干扰、天线、发射功率和法规状态；
- 真实传感器的噪声、延迟、漂移和安装误差；
- 真实设备上的看门狗、失联保护和机械执行结果。

因此，仿真记录结束后，如果任务要进入设备阶段，应新建一张设备验收卡，把硬件、固件、接口和环境重新记录。不要把仿真的标准输出直接当成硬件验收单。

## 6. 发布前的脱敏清单

逐项检查：

- 删除本机用户名、绝对路径、内网地址、真实主机名和设备序列号；
- 删除账号、密码、令牌、私钥和未公开的服务端点；
- 将 MAC 地址、SSID、项目内部编号改成占位符；
- 保留官方公开文档链接、访问日期和版本边界；
- 保留“来源记录”“本轮未运行”“结果待确认”等证据状态；
- 不发布项目原始配置、日志原件、抓包原件或设备照片中的识别信息。
