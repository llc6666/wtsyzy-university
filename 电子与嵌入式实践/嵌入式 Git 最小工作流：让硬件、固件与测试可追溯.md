# 嵌入式 Git 最小工作流：让硬件、固件与测试可追溯

> 目标：让别人能回答三个问题：这份固件对应哪块板、它由什么源码构建、测试结果来自哪一次构建。

## 何时使用

- 新建嵌入式工程或第一次把硬件项目放进 Git 时。
- 修改引脚、时钟、协议、PCB 或测试方式时。
- 准备把代码交给队友、比赛队伍或公开仓库时。

## 输入

1. 项目目录、实际硬件版本和当前任务。
2. 工具链、芯片包、依赖库和构建命令。
3. 能够描述通过与失败的最小测试集。
4. 公开范围、第三方许可证和需要排除的本地配置。

## 仓库最小结构

```text
project/
├─ README.md              # 构建、烧录、测试入口
├─ config/                # 配置文件和版本说明
├─ firmware/              # 源码
├─ hardware/              # 自有且获授权的原理图或链接
├─ tests/                 # 测试步骤与结果格式
└─ docs/                  # 板卡事实卡、变更和已知问题
```

构建产物、IDE 用户配置、日志、下载工具安装包、密钥和设备唯一标识默认不入库。实际项目可按工具链调整目录，但必须保留构建入口和版本对应关系。

## 操作步骤

### 1. 首次建库

```powershell
git init
git status
git add README.md firmware config docs tests
git commit -m "chore: initialize embedded project"
```

README 至少写：支持的硬件版本、工具版本、构建命令、烧录方式、串口参数和最小测试。

### 2. 一次只提交一类变化

把“改引脚”“修协议”“更新 PCB 版本”“补测试记录”拆成可读提交。提交消息写动词和对象，例如：

```text
feat: add uart echo for board-r1
fix: reject invalid command frame
docs: record adc sampling parameters
```

### 3. 每次集成前确认工作区

```powershell
git status
git diff -- firmware config docs tests
git diff --check
```

确认差异只属于当前任务，再执行：

```powershell
git add <明确的文件路径>
git commit -m "<说明本次可验证变化>"
git rev-parse --short HEAD
```

不要用 `git add .` 把未知二进制、临时文件或本地配置一起加入。

### 4. 把测试结果绑定到提交

测试记录至少填写硬件 ID、固件提交、工具版本、输入、期望、实际结果和原始证据。失败也要提交记录，避免队友重复走同一条错误路径。

### 5. 推送前做公开检查

检查密钥、账号、私有路径、成员信息、第三方原文和未授权工程；再检查 README 的构建步骤能否从干净目录执行。Git 的提交是暂存区内容的快照，未暂存的修改不会进入该提交。[官方手册](https://git-scm.com/book/en/v2/Git-Basics-Recording-Changes-to-the-Repository)

## 交付物

- 一份可读的 README。
- 一组按任务拆分的提交。
- 与提交号绑定的测试记录。
- 一张硬件、固件、工具链和产物对应表。

## 验收

- 新电脑能按 README 找到构建入口，并知道需要哪些工具版本。
- 每个可演示固件都能追溯到硬件 ID 和 Git 提交。
- `git status` 清楚，提交前差异经过检查。
- 公开仓库不包含私密配置、无授权资料和不可解释的二进制文件。

## 常见失败与修正

- **一次提交包含几十类修改**：按硬件、固件、文档、测试拆分，必要时回到暂存区重新选择。
- **固件文件名没有版本**：把硬件 ID、提交号和构建日期写进产物名或启动日志。
- **只提交通过结果**：保留失败输入、现象和下一步，失败记录也是排障资产。
- **把 Git 当网盘**：Git 记录文件变化，不替代物料管理、备份、许可证或硬件测试。

## 边界

本流程适用于学习项目和小团队开发。涉及量产、功能安全、密钥管理或受监管产品时，应再接入组织的评审、签名、制品库和访问控制流程。
