# 开源工具选型：从仓库入口到采用决定

有两三个开源工具看起来都能用时，先把任务、版本和证据写到一张卡上。以“给两台已获授权的电脑记录一次指定方向的 IP 网络吞吐”为例，能输出一个数还不够：记录要能说明这个数从哪里来、在哪些条件下成立。

## 1. 先写你的任务，划一条停止线

准备一个实际任务、目标环境和每个候选的公开入口。先填下面四行，再看功能列表。第一次筛选可以给每个候选设 15 分钟；到时没有找到关键证据就标为待核，不靠搜索摘要填空。

| 字段 | 示例 |
| --- | --- |
| 一个问题 | 两台自管电脑之间，在给定方向和时段内的 IP 网络吞吐是多少？ |
| 最小产物 | 一份带两端工具版本、方向、协议、时段和结果的记录 |
| 硬约束 | 只在获准的两台机器及网络上操作；当前任务只需独立工具，无需把源码或二进制打包交付 |
| 停止条件 | 用途不匹配即移除；来源、版本或目标平台资料缺失则暂缓；没有网络操作许可则只做文档筛选 |

## 2. 顺着官方入口查到同一个版本

1. **认上游。** 从项目官网或文档追到维护仓库，核对发行和反馈入口。镜像可以读代码；若镜像自述是只读的，找到它指向的上游再查发行或反馈。发现同名工具时同时记组织名和仓库名。
2. **对齐版本。** 选一个发行标签或提交，记录日期；让发布说明、使用文档和许可尽量指向同一版本。只有开发分支文档时，写明“该页不对应所选版本”。准备使用发行版打包的工具时，再核对包的实际版本和来源，别把上游版本号当成已安装版本。
3. **查目标环境。** 对着版本文档勾选系统、架构、依赖和输出字段，只填与任务相关的项目。文档明确支持可以写“文档支持”；缺少匹配信息填“待核”。CI 记录如果有，写清它覆盖的版本和环境。
4. **按使用方式查许可。** 先写你只准备单独使用，还是要链接、修改、随作品分发或引用文档。打开选定版本的 `LICENSE`，并查看涉及组件或文档的单独声明。仓库页面上的简短标签只作定位线索；缺少许可说明或适用范围不清时，停在“仅保留链接”，暂不复制或打包。

## 3. 把证据写成一句有条件的话

| 手里有什么 | 可以记录什么 | 还不能据此判断什么 |
| --- | --- | --- |
| 官方项目首页或 README | 项目身份与上游声明的用途 | 目标版本、平台兼容或本地可用 |
| 对应版本的发布说明、文档和许可文件 | 文档列出的功能、要求及许可入口 | 在你的环境中是否能完成任务 |
| 上游 CI 或他人运行记录 | 所列版本、环境和场景中的结果 | 换平台、改配置或换输入还能否成立 |
| 本地最小任务的原始结果 | 在记录的机器、环境和输入下观察到了什么 | 其他场景的性能或长期稳定性 |

同一个数字应能追到运行记录：例如“接收端的汇总值，某方向、某协议、某时段”。如果当前只有文档，结果栏留空，写“仅文档筛选”；不要把计划填进结果栏。

## 4. 筛一遍：iPerf3 与 ns-3

以下只演示如何下文档阶段的结论，不含实测值。公开资料核对日期：2026-11-21。

| 候选 | 文档能回答什么 | 对本任务的决定 |
| --- | --- | --- |
| iPerf3 | [ESnet 文档](https://software.es.net/iperf/)说明它可主动测量 IP 网络的吞吐等指标。用历史版本 [3.18 发布说明](https://github.com/esnet/iperf/releases/tag/3.18)和[同标签许可文件](https://github.com/esnet/iperf/blob/3.18/LICENSE)演示如何把版本与许可对齐；该版本仅供查阅示范。 | **进入试用候选**。先选适配目标平台的版本并查对应文档。实际使用后分开记录两端环境、方向、协议、时段和汇总口径；这里的吞吐不等于某个应用的业务成功率。 |
| ns-3 | [项目文档](https://www.nsnam.org/documentation/)分开发行版和开发树；[GitHub 镜像](https://github.com/nsnam/ns-3-dev-git)指向维护和反馈所用的 [GitLab 上游](https://gitlab.com/nsnam/ns-3-dev/)。它可用来观察指定网络模型中的结果。 | **从这道题排除**。任务要求两台现有机器的直接测量，模型输出不能填进实测栏。将来要比较模型参数时再开新卡，并另外核对版本和许可。 |

两个工具都可能产出网络指标，但各自回答的问题不同。把第一行任务改成“比较两个模型条件”，候选就要重筛。先问输出能否回答问题，再比较安装和维护成本。

## 留一张卡，交给下一位读者

```text
任务 / 目标环境 / 最小产物：
上游 / 发行标签或提交 / 核对日期：
本次用法 / 许可入口 / 待核的组件：
必需功能或输出字段 → 对应版本文档：
证据状态：仅登记 / 已查文档 / 已有运行记录
结果与适用条件（没有原始记录时留空）：
决定：进入试用 / 暂缓 / 排除
未解决的硬约束 / 谁在什么时候补证：
退路 / 何时重新评估：
```

自查时，请另一个人只拿这张卡，打开同一版本的入口、指出一条决定去留的证据，并说出哪个条件变化就得重查。任一项说不清，补链接或理由。版本、目标平台或分发方式变化时，重开对应检查项；候选均不满足硬约束时，缩小任务或保留已有方案，不凑一个“优胜者”。这张卡适合学习项目和小范围选型；正式生产接入还要按实际影响完成安全、维护与许可审查。

来源未提供运行验证记录；本轮仅整理，未执行测试。延伸阅读：[资料入库与来源卡片](../方法论/知识库构建/资料入库与来源卡片.md)、[项目开发闭环](项目开发闭环：先跑通最小链路，再扩大范围.md)。
