# 容器前置条件与下标边界：从运行时错误读修复线索

## 这篇笔记解决什么问题

程序能够编译，不代表运行时访问一定合法。常见表现包括：

- 编译成功，运行时在标准库头文件中触发断言；
- 官方样例通过，换一组输入后输出异常或程序崩溃；
- 错误写入发生在一个位置，堆损坏却在后面的内存操作中才暴露。

遇到这类现象，先判断“违反了哪个前置条件”，再决定修复方式。不要先把问题归因于编译器或标准库。

本页整理自个人 C++ 错误记录中的两个案例：空队列调用 `front()`，以及前缀和数组少开一格导致的越界写。个人路径、具体工程、训练台账和原始对拍脚本已删除。

> 来源未提供运行验证记录；本轮仅整理，未执行测试。

## 第一步：先按发生阶段分类

| 阶段 | 典型现象 | 先检查什么 |
| --- | --- | --- |
| 编译阶段 | 语法、类型、名称或链接错误，通常不会生成可运行产物 | 代码结构、头文件、类型和链接输入 |
| 运行阶段 | 已生成程序，但执行时异常终止、断言失败或输出异常 | 容器前置条件、下标、生命周期和输入边界 |
| 结果阶段 | 程序没有崩溃，但答案错误 | 不变量、状态更新顺序、溢出和边界 |

“编译通过”只能说明编译器接受了当前源代码，不能推出每个容器访问都合法。

## 第二步：从报错文字提取前置条件

标准库头文件里的报错位置往往只是“拦截点”。真正需要回到自己代码中查找的是调用处。

例如看到下面这种信息：

```text
std::queue<...>::front()
Assertion '!this->empty()' failed.
```

可以拆成四部分：

1. `front()`：发生了队头访问；
2. `!this->empty()`：调用前提是容器非空；
3. 标准库文件行号：标准库在这里发现了非法调用；
4. 自己的调用代码：需要检查是否在 `front()` 前保证了非空。

防御式写法应把前置条件写进控制流：

```cpp
while (!q.empty() && q.front() + window == i) {
    q.pop();
}
```

`&&` 从左向右短路。队列为空时，右侧的 `front()` 不会执行。这里的重点不是记住某个模板，而是把“访问前提”放到访问动作之前。

同一思路适用于：

| 访问动作 | 访问前应确认 |
| --- | --- |
| `queue.front()`、`queue.back()` | 队列非空 |
| `stack.top()` | 栈非空 |
| `vector.front()`、`vector.back()` | 容器非空 |
| `vector[i]`、数组 `a[i]` | `i` 在有效下标范围内 |
| `vector.at(i)` | `i < size()`，否则处理异常 |

不同容器的具体接口和异常行为应回到标准库文档确认。可参考 [std::queue::front](https://en.cppreference.com/cpp/container/queue/front)、[std::queue::empty](https://en.cppreference.com/cpp/container/queue/empty) 和 [std::vector::operator[]](https://en.cppreference.com/cpp/container/vector/operator_at)。

## 第三步：单独检查“元素数量”和“最大下标”

下标越界最容易出现在“循环次数”和“容器大小”没有对齐时。

错误模式：

```cpp
std::vector<long long> prefix(n, 0);  // 合法下标：0 到 n - 1
for (int i = 1; i <= n; ++i) {
    prefix[i] = prefix[i - 1] + value;
}
```

循环最后一次会写入 `prefix[n]`，但容器只分配了 `n` 个元素。若要同时保存 `prefix[0]` 和 `prefix[n]`，应先按使用的最大下标分配：

```cpp
std::vector<long long> prefix(n + 1, 0);  // 合法下标：0 到 n
for (int i = 1; i <= n; ++i) {
    prefix[i] = prefix[i - 1] + value;
}
```

写代码前先列一张下标表：

| 对象 | 元素数量 | 最小下标 | 最大合法下标 | 循环是否会访问尾端 |
| --- | ---: | ---: | ---: | --- |
| `vector<T>(n)` | `n` | `0` | `n - 1` | 检查是否出现 `i == n` |
| `vector<T>(n + 1)` | `n + 1` | `0` | `n` | 可用于保存前缀和 `s[0]...s[n]` |

不要用“只越界一格”降低风险。`operator[]` 越界访问可能没有立即表现，后续分配或释放内存时才暴露，错误位置和崩溃位置因此可能相距很远。cppreference 将越界使用 `vector::operator[]` 归为未定义行为；这也是“样例通过”不能证明下标正确的原因。[参考：`std::vector::operator[]`](https://en.cppreference.com/w/cpp/container/vector/operator_at)

## 第四步：把修复写成可复用规则

不要只记录“这一题改了哪一行”，把错误抽象成访问规则：

| 错误模式 | 复用规则 | 修复动作 |
| --- | --- | --- |
| 空容器调用 `front/back/top/pop` | 先保证容器非空 | 在访问或删除前增加状态判断 |
| `vector(n)` 却访问 `0...n` | 元素数量和最大下标不是同一个概念 | 按最大下标倒推分配数量 |
| 依赖 `operator[]` 自动报错 | 普通 `operator[]` 不负责边界检查 | 代码中显式维护范围，必要时使用带检查接口 |
| 只用官方样例判断安全 | 样例可能没有覆盖空容器和尾端下标 | 补写“哪条前提会被击穿”的输入说明 |
| 关闭调试检查后不再崩溃 | 不崩溃不等于访问合法 | 保留原始前置条件判断，不能把关闭检查当修复 |

## 第五步：区分“来源记录”和“本轮结论”

这类笔记常常同时包含源代码、报错、修复和测试结果。整理时应把证据层次分开：

```text
来源记录：某次运行记录了什么现象，以及当时采用了什么修复。
公开解释：这个现象可以抽象成什么访问前提或边界规则。
读者动作：读者应检查哪一个容器、哪个最大下标和哪条循环边界。
未完成事项：当前页面没有替读者运行代码，也没有证明读者自己的程序正确。
```

来源中已有的编译、运行或对拍数据，只能标记为“来源记录”。没有来源数据时，写“来源未提供运行验证记录；本轮仅整理，未执行测试”，不要补写测试数量、输出或性能结论。

如果读者需要进一步排错，可以自行选择调试构建。GNU libstdc++ 文档说明，`-D_GLIBCXX_DEBUG` 会启用其调试模式；具体支持范围、编译方式和跨翻译单元限制应以自己的工具链文档为准。[GCC libstdc++ Debug Mode](https://gcc.gnu.org/onlinedocs/libstdc++/manual/debug_mode_using.html)

## 一张可直接使用的排错卡

```text
现象：编译失败 / 运行时终止 / 输出异常 / 结果偶尔错误

1. 错误发生在编译、运行还是结果阶段？
2. 报错中是否出现 empty、front、back、top、subscript、out-of-range？
3. 出错调用前，容器是否可能为空？
4. 容器分配了多少个元素？循环访问的最大下标是多少？
5. 下标、迭代器或引用是否在容器修改后仍然有效？
6. 现象是来源记录，还是本次读者已经独立确认的结果？
7. 修复后留下哪条可复用规则？
```

- 这套排错卡只能帮助定位容器前置条件和常见下标边界，不能替代算法证明、完整代码审查或运行时诊断工具。
- 同一个错误在不同编译器、标准库版本、编译参数和平台上的表现可能不同；不要根据“这里没有崩溃”推断代码安全。
- 关闭断言或切换优化级别只能改变错误暴露方式，不能修复未定义行为。
