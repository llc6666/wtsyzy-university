# STM32 最小实验：从资料核对到串口回显

> 目标：在不假设具体板卡引脚的前提下，完成一次“资料核对，构建，烧录，复位后串口回显”的最小闭环。它证明的是工具链、供电、调试和通信链路都可用，不等于项目已经完成。

## 何时使用

- 第一次使用一块 STM32 开发板或更换板卡版本时。
- 烧录、LED 或串口中任一环节失败，需要建立可信基线时。

## 输入

1. MCU 完整型号、封装和开发板版本。
2. 对应的数据手册、参考手册和板卡原理图链接或文件版本。
3. 已知可用的供电方式、调试器和 USB 转串口模块。
4. 工具链名称与版本：配置工具、编译器或 IDE、烧录工具。
5. 一个空 Git 仓库，不含他人固件、破解工具或未知二进制文件。

## 操作步骤

### 1. 先写板卡事实卡

在上电前填完下表。无法确认的字段写“待验证”，不要凭开发板照片补全。

| 字段 | 要记录的值 |
| --- | --- |
| MCU 与封装 | 完整型号、封装 |
| 板卡版本 | 丝印、购买页或原理图版本 |
| 供电 | 电压、供电口、允许来源 |
| 调试接口 | SWD/JTAG 或其他接口、引脚对应来源 |
| 串口接口 | 使用的 UART、TX/RX/GND 对应来源 |
| 工具链 | 工具名称、版本、芯片包版本 |

### 2. 从官方文档建立工程

1. 在配置工具中选择**实际 MCU 或实际开发板**，保存配置文件到仓库。
2. 只启用一个 GPIO 输出和一个 UART；引脚、时钟和波特率以原理图及芯片约束为准。
3. 生成工程后立即构建一次。构建失败时先保存完整报错和工具版本，不要换多个教程工程碰运气。
4. 在用户代码区加入两项最小行为：GPIO 周期翻转；复位时通过 UART 输出固定启动标识，例如 `boot: board=<版本>`。

STM32CubeMX 可以配置引脚、时钟、外设并生成初始化工程；生成代码只能作为起点，实际引脚与电气连接仍需回到板卡原理图核对。[官方文档](https://dev.st.com/stm32cube-docs/stm32cubemx/6.18.0/en/index.html)

### 3. 烧录并验证

1. 断电后按原理图连接调试器和地线，确认没有接反供电。
2. 使用官方烧录工具连接目标，记录连接接口与目标芯片识别结果。
3. 烧录后执行校验；STM32CubeProgrammer 支持烧录和存储器校验，但具体接口是否可用取决于芯片和板卡。[官方文档](https://dev.st.com/stm32cube-docs/prog/2.23.0/en/docs/markup/CubeProg_How_To_Start/CubeProg_HowToStart_toc.html)
4. 复位开发板，记录 LED 周期和串口的首行日志。串口日志需包含工程 Git 短提交号或手工版本号，避免把旧固件当成当前构建。
5. 断电再上电，重复至少三次；三次都得到同样的 LED 与日志现象才通过。

## 交付物

- `board-facts.md`：板卡事实卡。
- 配置文件、源码和可重建工程。
- 烧录与校验记录。
- 三次复位的串口日志或原始终端保存文件。

## 验收

- 编译器返回成功，烧录工具识别的芯片型号与事实卡一致。
- 三次冷启动均能观测到指定 GPIO 行为和同一格式的串口启动标识。
- 串口参数、TX/RX/GND 接线和日志文件路径均有记录。
- 任一人按记录重新构建后，不依赖原作者口述也能完成一次验证。

## 常见失败与修正

- **调试器无法连接**：依次核对公共地、供电、调试引脚、复位与启动配置；不要先重装 IDE。
- **能烧录却无现象**：先确认写入的是否是当前构建产物，再检查 GPIO 逻辑、电路是否为低电平点亮以及板载 LED 实际连接。
- **串口乱码**：两端必须同时核对波特率、数据位、校验、停止位和 TX/RX 方向；串口模块电平必须匹配 MCU 允许范围。
- **只跑一次就宣布成功**：至少完成三次断电重启，并保存日志。

## 边界

本页不提供任何具体芯片的引脚号、供电电压或启动跳线位置。它们随型号与板卡版本变化，错误接线可能损坏设备；上电前必须以数据手册和实际原理图为准。
