# 共用体：一块内存的多种读法

## 1. union 与 struct 的根本区别

结构体的成员按顺序分别占用存储，共用体的成员共享同一段存储：

~~~c
union WordBytes {
    uint32_t word;
    uint8_t bytes[4];
};
~~~

共用体的大小至少能够容纳最大成员，并可能受对齐要求影响。写入一个成员后，其他成员对应的是同一块字节；它们不是几份互不相关的数据。

适合先问一句：

- 这些字段要同时存在吗？同时存在用 struct。
- 同一份数据需要几种互斥解释吗？可以考虑 union。

## 2. 三类常见用途

### 整体值与字节序列

~~~c
union WordBytes w = {0};
w.word = 0x12345678;
~~~

这个写法可以帮助观察或组织字节，但字节先后顺序由目标平台的字节序决定。协议通信时不要把主机内存布局直接当成线上协议，协议应明确规定大端或小端，并在收发两端显式转换。

### 省空间的互斥状态

~~~c
union PacketView {
    uint8_t raw[32];
    struct {
        uint8_t type;
        uint8_t length;
        uint8_t payload[30];
    } parsed;
};
~~~

如果程序明确保证某一时刻只使用一种视图，union 可以让两种视图共享空间。否则读者很难知道当前有效成员，调试成本会高于节省的字节。

### 检查位级表示

把浮点和整数放进同一个 union，可以观察位表示，但这不等于数值转换。跨成员读取的结果、别名规则和可移植性必须结合 C 标准、编译器和目标平台判断。需要可移植的数值转换时，优先使用显式转换或 memcpy 复制对象表示，并写清目标格式。

## 3. struct、union 与位域的组合

~~~c
typedef union {
    uint32_t all;
    struct {
        uint32_t mode : 3;
        uint32_t enable : 1;
        uint32_t reserved : 28;
    } bits;
} ControlWord;
~~~

这种写法常用于描述寄存器或协议字段，但位域的布局、分配方向和基础类型规则存在实现相关性。它适合与目标编译器、芯片手册和已有工程约束一起使用，不能仅凭 C 源码推断所有硬件行为。

## 4. 危险边界

| 写法 | 处理原则 |
| --- | --- |
| 写成员 A，再读成员 A | 正常的当前成员访问 |
| 写整体值，再按字节查看 | 依赖目标字节序和实现；先写明平台假设 |
| 写 A，读 B 当作数值转换 | 不要这样表达数值换算；位级重叠不等于数值相等 |
| 忘记当前有效成员 | 可能得到不可用或实现相关的解释 |
| 用 union 直接拼线上协议 | 受字节序、对齐、填充和编译器影响 |

## 5. 写代码前的检查卡

1. 当前有效成员是哪一个，谁负责切换它？
2. 共用体是否真的节省了空间，还是制造了更大的状态复杂度？
3. 跨平台或通信场景是否明确字节序？
4. 是否把位域布局误当成协议或寄存器的强保证？
5. 如果需要数值转换，是否应该改用显式转换或 memcpy？
6. 对目标编译器和芯片手册的依赖是否已经写在接口说明中？
