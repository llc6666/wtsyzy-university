# 硬件实验记录与故障定位

> 目标：把“板子没反应”变成可测、可比较、可复现的问题。实验记录先描述事实，再给判断；没有测量或日志的推测必须标为待验证。

## 何时使用

- 每次接入新模块、修改接线、升级工具链或改变固件后。
- LED、串口、I2C、SPI、PWM、ADC 等外设现象与预期不一致时。

## 输入

1. 当前板卡事实卡、原理图版本和器件数据手册。
2. 当前固件提交号、配置文件和构建日志。
3. 可用测量工具：万用表为最低要求；需要时使用逻辑分析仪或示波器。
4. 一个单句、可观察的预期，例如“复位后 1 秒翻转一次 LED”。

## 实验卡模板

```markdown
## 实验：<动词化目标>

- 日期：YYYY-MM-DD
- 板卡与版本：
- MCU / 外设型号：
- 原理图 / 数据手册：链接或版本号
- 供电与接线：电压、公共地、关键引脚
- 固件提交：
- 工具链：配置工具、编译器、烧录工具版本
- 预期现象：
- 实际现象：
- 原始证据：日志、照片、波形、测量值路径
- 当前判断：已验证 / 待验证
- 下一步最小动作：
```

## 故障定位步骤

### 1. 固定变量

一次只改一类变量：接线、配置、代码或工具版本。改动前提交当前状态；改动后写清改了什么。多个变量同时变化时，即使现象变好也无法知道原因。

### 2. 从电源和物理连接开始

1. 断电检查短路、反接、松动线和公共地。
2. 上电后测量供电点，而非只相信 USB 已连接。
3. 核对板卡实际丝印与引用的原理图版本。
4. 调试器、串口模块和目标板共地后，才检查通信设置。

### 3. 把系统缩到单一闭环

保留一个输入和一个输出：例如固定串口字节换一个 GPIO 电平，或固定 ADC 输入打印原始采样值。先排除显示、协议解析、状态机等上层复杂度。

### 4. 逐层观察

| 层级 | 先问什么 | 最低证据 |
| --- | --- | --- |
| 供电 | 电压是否到芯片和模块？ | 测量值和测点 |
| 烧录 | 当前固件是否真正写入？ | 目标识别、校验结果、版本日志 |
| MCU 配置 | 时钟、复位、引脚复用是否一致？ | 配置文件和原理图对照 |
| 外设信号 | 波形或字节是否实际出现？ | 波形、逻辑分析或原始日志 |
| 应用逻辑 | 输入是否改变了期望状态？ | 关键状态变量和输出日志 |

### 5. 用反证结束本轮

每一轮只写一个可推翻的判断，例如“若 UART 已进入中断，则日志计数每次接收会加一”。执行测试后写结果：支持、否定或信息不足。信息不足时下一步是新增测量，不是继续猜测。

## 交付物

- 一张实验卡。
- 至少一份原始证据：串口日志、测量表、波形或照片。
- 一个明确的下一步最小动作，或一条已被证伪的假设。

## 验收

- 第三方能区分预期现象、实际现象与作者的解释。
- 任何“已修复”结论都有复位或重复测试记录。
- 关键接线、供电与固件版本可以追溯。

## 常见失败与修正

- **先改大量代码**：回退到最小闭环，一次只动一个变量。
- **只截一张 IDE 图**：补上实际板卡现象、日志或测量值。
- **把串口打印当作所有层都正常**：它只能证明特定路径执行过，仍需核对电平、时钟或外设波形。
- **重复烧录不同来源的固件**：给每个构建产物写版本标识，并记录其 Git 提交。

## 边界

低压开发板也可能因反接、短路、错误电平或错误供电受损。无法判断电气安全时先断电，查原理图与器件额定参数；本页不能替代实验室安全规范或设备数据手册。
