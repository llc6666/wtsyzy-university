# 递归排错：区分死路、数组容量与状态破坏

## 这篇笔记解决什么问题

递归搜索出现“程序正常结束但答案变少”时，问题可能同时来自三层：状态定义错了、死路没有及时退出、写入位置超出数组范围。只盯着最终输出，通常很难判断是哪一层先失效。

这篇笔记把一类自然数拆分练习中的排错过程抽象成通用方法，适用于“逐层填写候选值”“维护剩余量”“用数组保存当前路径”的回溯程序。重点是建立状态契约和边界推导，不提供某道题的完整题面或个人训练记录。

> 来源记录含编译、样例、边界和对拍结果；这些结果属于来源历史记录。本轮只做筛选、改写和公开边界处理，未重新编译、运行或对拍。

## 一、先给递归状态分成三类

假设搜索函数维护两个量：`position` 表示下一个待填写的位置，`remaining` 表示距离目标还差多少。每次选择候选值后，递归进入下一层并减少 `remaining`。

`remaining` 至少有三种语义：

| 状态 | 含义 | 动作 |
| --- | --- | --- |
| `remaining < 0` | 已经超过目标，继续向下不可能恢复 | 立即返回 |
| `remaining == 0` | 当前路径恰好达到目标 | 按要求输出或记录，然后返回 |
| `remaining > 0` | 仍有机会达到目标 | 继续枚举候选 |

可以先用伪代码写清楚控制流，再写具体循环：

```text
search(position, remaining):
    if remaining < 0:
        return                 // 死路
    if remaining == 0:
        emit current path      // 成功
        return
    for each candidate allowed by the invariant:
        write candidate at position
        search(position + 1, remaining - candidate)
```

这里的关键不是“多写一个判断”，而是把“成功”和“失败”都当作终止状态。只判断 `remaining == 0`，会把已经超出的路径误当成“还可以继续试”。

### 不变量要写成句子

在递归函数上方写出以下句子，任何一条说不清，代码就还没有准备好：

1. `position` 指向下一个要写入的位置，还是最后一个已经写入的位置？
2. `remaining` 是“已累计的量”，还是“还差的量”？
3. 当前路径是否必须非递减、不能重复，或必须满足固定长度？
4. 进入下一层后，哪个量一定更接近终点？
5. 哪些状态是成功，哪些状态是死路，哪些状态可以继续展开？

## 二、把“错误输出”还原成因果链

递归程序常见的症状和优先排查方向如下：

| 症状 | 先问什么 | 可能的根因 |
| --- | --- | --- |
| 完全没有结果 | 是否真的能抵达成功状态 | 剩余量更新错误、成功条件写错 |
| 只输出极少结果 | 失败分支是否改变了搜索条件 | 死路继续向下、共享状态被覆盖 |
| 返回码为 0 但答案错误 | 是否把“正常结束”误当成“逻辑正确” | 未定义行为没有立刻崩溃，或搜索提前收窄 |
| 递归深度异常增加 | 每条路径是否有明确的进展量 | 负剩余量没有退出、候选下界未收紧 |
| 输出顺序错 | 题目顺序要求是否已经编码进枚举顺序 | 先生成后排序、递归循环方向不一致 |

一个典型的错误链条是：

```text
剩余量变成负数
    ↓ 没有作为死路返回
递归继续增加 position
    ↓ 写入位置超过数组容量
相邻的共享状态可能被改写
    ↓ 下一轮循环边界发生变化
输出变少或顺序异常
```

“相邻变量被改写”只能作为一种可能的内存布局解释，不能把它当成 C++ 语言保证。数组越界属于未定义行为，具体表现可能是错误输出、崩溃、看似正常结束，或者在另一处才暴露。Microsoft 的代码分析文档也明确把超出数组最大边界的索引与未定义行为、潜在崩溃联系起来，并提醒数组下标从零开始，最大合法下标是元素个数减一：[Warning C6200](https://learn.microsoft.com/en-us/cpp/code-quality/c6200?view=msvc-170)、[Warning C6201](https://learn.microsoft.com/en-us/cpp/code-quality/c6201?view=msvc-170)。

因此，下面三句话不能互相替代：

- 进程返回码为 0，只说明进程按该次执行路径结束，不能证明答案正确。
- 编译器没有报数组越界，也不能推出所有运行路径都在边界内。
- 某次运行看起来正常，只能说明该次运行没有暴露问题，不能证明未定义行为不存在。

## 三、按最坏路径估数组容量

数组容量应该从“可能写入的最大位置”倒推，而不是凭常见输入猜一个数字。

| 写法约定 | 可能访问的最大位置 | 至少需要的元素数 |
| --- | ---: | ---: |
| 从 `a[0]` 开始，最大下标为 `d - 1` | `d - 1` | `d` |
| 从 `a[1]` 开始，最大下标为 `d` | `d` | `d + 1` |
| 还需要尾后位置或哨兵槽 | `d` 或更大 | 按实际用途再加一格 |

递归深度的估计要看最小候选值。若每层至少可以选择 `1`，目标量为 `n` 时，“全选最小值”的路径可能比“只选两个数”的路径深得多。固定数组至少要满足：

```text
最大可能写入下标 < 数组元素数量
```

如果最大深度来自运行时输入，可以优先考虑以下设计：

1. 用 `std::vector` 按已知上界创建路径空间。
2. 将“当前路径、当前位置、剩余量”放入一个明确的状态对象，减少无关全局变量。
3. 让函数参数或状态对象表达容量契约，避免靠相邻全局变量维持程序运行。
4. 在写入前保留显式边界条件；边界条件是程序逻辑的一部分，不是调试阶段的临时补丁。

C++ Core Guidelines 将数组越界归入 bounds safety，并把“访问超出数组范围”列为应当避免的边界违规；它还给出了对索引范围进行静态约束的方向：[C++ Core Guidelines：bounds profile](https://isocpp.github.io/CppCoreGuidelines/)。

## 四、把排错过程拆成六步

### 第 1 步：固定现象，但不急着改循环

记录输入、输出形态、退出状态和递归层数等事实。先标记这些事实来自“来源记录”还是“读者当前运行”，不要把两者混写。

### 第 2 步：画出状态转移

对每个递归参数写出：初始值、每次递归如何变化、成功条件、死路条件。特别检查“剩余量变负后是否仍会展开”。

### 第 3 步：单独审查写入位置

列出数组的元素数量、起始下标、最大可能深度和每一次写入表达式。不要只看正常答案路径，要看失败路径是否也会执行写入。

### 第 4 步：隔离共享状态

把目标值、循环上界和当前路径分开表达。能用局部变量或状态对象表达的内容，不要让递归函数依赖一组互相邻近的可变全局变量。

### 第 5 步：检查输出顺序的来源

如果题目要求字典序、稳定顺序或按时间顺序输出，要说明顺序是由候选枚举顺序直接保证，还是在全部结果生成后再排序。两者的内存和实现边界不同。

### 第 6 步：再选择工具辅助定位

读者需要进一步定位时，可以根据自己的工具链选择调试器、运行时检查或标准库调试模式。GCC 的 libstdc++ Debug Mode 可对部分容器、迭代器和算法前置条件提供额外检查，但它只覆盖能够检查到的标准库使用错误，不能替代状态证明和数组容量推导：[GCC libstdc++ Debug Mode](https://gcc.gnu.org/onlinedocs/libstdc%2B%2B/manual/debug_mode.html)。

## 五、递归代码审查卡

把下面这张卡贴在递归练习旁边，逐项写答案：

```text
目标：搜索什么对象？
状态：每个参数分别表示什么？
成功：哪一个条件表示可以输出？
死路：哪些条件表示继续向下没有意义？
进展：每次递归调用后，哪个量必然向终点靠近？
约束：当前路径的不重复、不下降或固定长度规则是什么？
容量：最坏路径会写到哪个下标？数组是否覆盖该下标？
共享状态：哪些变量可能被递归层或失败分支改变？
顺序：输出顺序由什么不变量保证？
证据：当前结论来自源码阅读、来源记录，还是读者独立运行？
```

## 六、读者可以如何自查

这篇笔记不替读者运行程序。读者可以在自己的环境中按下面顺序操作：

1. 先用一组最小输入手算所有可能路径，标出成功和死路。
2. 在纸上写出递归深度上界与数组最大合法下标。
3. 给每次写入补上索引契约，确认失败路径也满足契约。
4. 将目标值和循环边界暂时设为不可被递归过程意外修改的状态。
5. 需要工具辅助时，分别记录编译结果、进程状态、输出内容和边界诊断，不把其中一项当成完整正确性证明。
6. 修复后再写一条“为什么这个修复阻断了错误链条”的解释，而不是只记录改了哪一行。
