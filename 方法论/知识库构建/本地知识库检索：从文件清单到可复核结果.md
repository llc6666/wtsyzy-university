# 本地知识库检索：从文件清单到可复核结果

## 适用场景

当笔记分散在多个本地目录，单靠文件名搜索会遇到三个问题：搜不到改写后的问法，搜到了过期页面，或者把来源原文、个人记录和可复用知识混在一起。本方法把检索拆成“清单、词法、语义、复核”四层，目标是找到应该阅读的候选页面，而不是让搜索结果替你下结论。

适合检索 Markdown 笔记、代码说明、实验记录和研究页面。涉及个人信息、原始附件或第三方资料时，先按公开边界和隐私规则分层，不要为了提高召回率而把所有文件都放进索引。

## 你需要准备什么

- 两个或更多需要检索的本地资料根目录，并为每个根目录设置稳定的短标签。
- 一份允许检索的范围表：哪些层可以进入词法索引，哪些页面只能保留在来源层，哪些路径永久排除。
- 页面中的最小元数据：`status`、`evidence_status`、`updated`、`source_type` 等。缺失字段要记录为“未声明”，不能自动解释成“已验证”。
- 一个独立的派生缓存目录，并将它加入忽略规则。索引可以删除重建，原始笔记不能被索引脚本改写。
- 一组带预期结果的回归题，至少覆盖精确关键词、符号或代码标识符、自然语言改写和同名页面区分。

## 第一步：先建立文件清单

不要从全文搜索直接开始。先为每个文件登记以下字段：

| 字段 | 用途 |
| --- | --- |
| 根目录标签、相对路径 | 定位页面，避免公开结果暴露本地绝对路径 |
| 文件类型、字节数 | 排除空文件、超大手册和不应进入文本索引的二进制 |
| 层级与索引策略 | 区分知识页、研究页、来源转录、计划台账和排除项 |
| 内容 SHA-256 | 查询时判断索引是否仍对应当前原文 |
| 稳定 ID | 文件改名或迁移后，尽量保留同一条记录的历史连续性 |
| `status`、`evidence_status`、更新时间 | 让结果带着证据状态返回，而不是只有标题和摘要 |

清单只记录路径和必要元数据。不要把原始附件复制进索引，也不要把索引缓存当作新的事实来源。个人档案、联系方式、名单、训练台账、备份、构建产物和来源转录应有明确的排除策略；来源转录即使允许检索，也应默认与知识页分开。

## 第二步：建立词法检索层

词法层负责精确匹配标题、术语、符号和代码标识符。一个实用的最小实现是：

1. 按 Markdown 标题切分章节，把文件名、章节名和正文写入全文索引。
2. 对中文短语、变量名和 API 名称使用适合子串检索的分词策略。SQLite FTS5 的 `trigram` tokenizer 可以作为一种实现选择，具体行为以官方文档为准。
3. 查询时按根目录、层级、`status` 和 `evidence_status` 过滤。
4. 默认排除来源转录和已取代页面，需要时再用明确开关查询。
5. 返回相对路径、章节、行号、证据字段、摘要和当前哈希是否新鲜。

词法层的优点是可解释：结果为什么命中，可以回到关键词和章节。缺点是它不擅长把“数字到底代表长度还是初始值”匹配到只写了“容器初始化”的页面。遇到这种情况，再进入语义层；不要先把词法结果数量当成检索质量。

命令接口可以保持简单，示例：

```powershell
python search.py build
python search.py query "vector 初始化" --vault coding
python search.py query "UART 日志边界" --vault embedded --limit 5
python search.py evaluate retrieval-cases.json
```

## 第三步：只对审查通过的页面做语义试点

语义检索适合处理同义改写和自然语言问句，但它会把“文字相似”误当成“证据相关”，所以必须先做白名单：

- 只选择已经经过人工审查的知识页、第一方技术解释和精选实验页。
- 排除个人名单、简历、来源原文、社团原件、备份、构建产物、规划台账和已取代页面。
- 优先在本机运行嵌入模型，接口限定为本地地址；不要把私有正文发送到云端服务。
- 每条向量同时保存页面 ID、相对路径、原文哈希、模型摘要和向量维度。
- 查询前再次核对原文哈希；哈希变化、模型摘要变化或维度变化时，停止使用旧索引并重建。

文档级试点可以先把标题、章节名和正文前一段固定长度文本拼成一个向量。长文后半部分可能因此无法命中，不能据此断言“资料不存在”；需要更高覆盖率时，再单独测试章节级向量。余弦相似度只能排序候选，不能证明页面中的事实正确，也不能替代来源复核。

本地试点的命令可以是：

```powershell
python semantic_pilot.py build
python semantic_pilot.py query "为什么采样数据需要先确认缓存和时钟" --vault embedded
python semantic_pilot.py evaluate retrieval-cases.json
```

## 第四步：合并结果，但保留证据边界

词法结果和语义结果适合互补：词法结果保留精确标识符，语义结果补足改写问句。可以使用基于名次的融合，例如让第 `r` 名贡献 `1 / (60 + r)`，把两个列表中的同一页面合并后重新排序。名次融合比直接比较不同模型的原始分数更容易解释。

融合后仍然要做三次检查：

1. 页面是否来自允许的层级，是否把来源原文或个人记录泄漏到默认结果。
2. 页面哈希是否新鲜，是否已经标记为 `superseded` 或待核验。
3. 结果能否回到原文、来源和适用边界。搜索摘要只用于定位，不作为结论证据。

## 第五步：用回归题验证检索是否真的改善

建立一个小型 JSON 测试集，每道题至少包含：

```json
{
  "query": "自然语言或精确关键词",
  "vault": "notes",
  "expected_path": "相对路径/目标页面.md"
}
```

测试集应混合以下问题：

- 标题、函数名、寄存器名等精确检索。
- 中文同义改写和口语问法。
- 同一术语在知识页、来源页和个人记录中的边界区分。
- 页面更新后旧索引是否被识别为过期。
- 需要日期或证据等级的时效问题。

记录 `recall@5` 或相同口径的前五命中率，并同时记录样本数、候选范围、错误召回和证据层泄漏。一个只有几十道手工题的回归集，只能说明这组题上的表现，不能外推到所有用户问题，更不能证明知识内容正确。

## 维护与失败处理

| 现象 | 原因 | 修正动作 |
| --- | --- | --- |
| 精确术语能搜到，自然问句搜不到 | 词法层依赖字面重合 | 增加语义候选，或给查询补充核心术语 |
| 结果混入个人记录或来源转录 | 白名单和默认过滤过宽 | 收紧路径规则，给来源层单独开关 |
| 结果显示但摘要写着过期 | 原文哈希已经变化 | 先重建词法索引，再按模型状态重建语义索引 |
| 长页面只命中前半部分 | 文档级向量截断了正文 | 评估章节级切分，不要据漏检断言不存在 |
| 缺少 `evidence_status` 的页面排在前面 | 元数据不完整 | 保留“未声明”状态，回到原文核验 |
| 重建时提示文件被占用 | 查询进程仍持有 SQLite 文件 | 关闭查询后串行重建，避免并发替换 |
| 搜索结果看起来合理但无法解释 | 只看相似度，没有回读原文 | 强制返回路径、章节、行号和证据状态 |

每次源目录批量变化后，按“词法索引 → 回归测试 → 语义试点”的顺序执行。生成的 SQLite、manifest 和向量库放在被忽略的缓存目录，不提交到 Git；提交前使用 [公开知识库的脱敏与发布检查](../公开发布/公开知识库的脱敏与发布检查.md) 检查路径、个人信息、来源内容和生成物。

## 最终验收清单

- [ ] 每个索引文件都有相对路径、层级、哈希和索引策略。
- [ ] 个人资料、备份、二进制和不应混排的来源层有明确排除规则。
- [ ] 默认查询不会把来源转录、已取代页面或个人记录混入知识结果。
- [ ] 词法结果能回到章节和行号，语义结果能回到原文和当前哈希。
- [ ] 语义模型、向量维度和模型摘要已记录，模型变化会触发重建。
- [ ] 回归题同时包含精确词、改写问句和边界问题，并记录样本范围。
- [ ] 生成缓存已加入忽略规则，源笔记保持只读或可回退。
- [ ] 搜索结果只负责定位，关键事实仍经过来源、日期和证据状态复核。

## 来源与复核要求

- [SQLite FTS5 官方文档](https://www.sqlite.org/fts5.html)：核对全文检索、tokenizer 和查询行为。
- [Ollama Embeddings 官方文档](https://docs.ollama.com/capabilities/embeddings)：核对本地嵌入接口和模型使用方式。
- 具体实现应保留自己的回归题、构建日志和模型摘要；不要把本文的示例命中率当成通用性能承诺。
