# 项目开发闭环：先跑通最小链路，再扩大范围

## 何时用

你要做一个工具、课程项目、开源作品或自动化流程，已经有想法，却还无法回答三件事：主流程能否跑通、当前版本凭什么可信、扩大范围会不会让项目失控。

本页适合单人和小团队的早期到中期开发。目标是把项目推进从“完成了一堆任务”变成一组可复查的交付物。

## 先准备四样东西

1. 一张[项目卡](../方法论/决策与项目/项目定义与验收.md)：目标、范围、截止日和验收条件已经写清。
2. 一条主流程：用户从输入到得到结果的最短路径。
3. 一个可重复的测试输入，以及可判断对错的预期结果。
4. 一个可独立复核的人、同学或 Agent；若暂时没有，至少准备一份固定检查表和干净的复现环境。

例如，做“文件去重工具”时，主流程可以限定为：选择一个目录 → 列出重复文件 → 用户确认 → 输出一份清单。删除文件、图形界面、云同步都先放进“本次不做”。

## 按五步推进

### 1. 把最小链路写成可执行句子

用这个格式写下第一版：

```text
给定 [输入]，系统经过 [一个核心处理]，输出 [可检查结果]；
当 [验收条件] 成立时，这条链路通过。
```

把它拆成四格，缺一格就先补定义：

| 环节 | 要写的内容 | 示例 |
| --- | --- | --- |
| 输入 | 格式、来源、合法范围 | 一个本地测试目录 |
| 处理 | 本版唯一必须实现的规则 | 按内容摘要分组 |
| 输出 | 人能打开或机器能读取的产物 | CSV 清单 |
| 验收 | 如何判断通过 | 已知重复文件被正确列出 |

第一版只允许有一条主路径。遇到异常输入时可以先报错并记录，不能为所有假设场景提前堆功能。

### 2. 为每个外部依赖写降级路径

外部依赖包括网络接口、账号、模型服务、第三方库、特定设备和他人提供的数据。对每项关键依赖填一行：

| 依赖 | 当前用途 | 失效信号 | 降级方案 | 复核动作 |
| --- | --- | --- | --- | --- |
| 公开接口 | 获取样例数据 | 超时或限额 | 改用固定本地样例 | 记录接口版本与请求时间 |
| 第三方库 | 解析文件 | 构建失败 | 锁定已验证版本或换标准库方案 | 重新安装后跑最小测试 |

没有降级方案的依赖不一定要移除，但必须写进风险栏。依赖变更进入代码库时，要看清新增、升级和删除的包及其漏洞、许可证信息；GitHub 的依赖审查可辅助查看这些变化，仍需阅读实际 diff。[GitHub：依赖审查](https://docs.github.com/en/code-security/concepts/supply-chain-security/dependency-review)

### 3. 小步改动，每步留一条证据

一次只完成一个可验证改动。每次改动后记录下面五项：

```markdown
日期：
改动：
影响范围：
验证命令或操作：
结果与未解决问题：
```

证据要匹配风险：

| 改动类型 | 最低证据 |
| --- | --- |
| 文案或配置 | diff 和人工复读 |
| 业务逻辑 | 代表性输入、预期输出、实际输出 |
| 依赖升级 | 构建结果、关键路径测试、依赖差异 |
| 数据处理 | 输入行数、输出行数、字段检查、抽样核对 |
| 发布版本 | 提交号、构建产物版本、部署后的实际访问或运行记录 |

需要确认文件在传递过程中没有变化时，可以记录摘要值。摘要用于发现内容是否改变，不用于证明文件内容正确；NIST 的安全散列标准定义了用消息摘要检测消息变化的用途。[NIST：Secure Hash Standard](https://csrc.nist.gov/pubs/fips/180-4/upd1/final)

### 4. 把生产和审查分开

提交者完成开发后，审查者只拿交接包，不依赖口头说明。交接包固定包含：

```text
输入：测试数据、环境要求、版本号
输出：可运行产物、截图或实际输出
修改：本轮文件与行为变化
未完成：已知缺口、风险、没有验证的场景
```

审查顺序：

1. 先复述目标和验收条件，确认审查对象没有跑偏。
2. 在可用时先运行最小链路，再查看实现和 diff。
3. 按输入、输出、异常、权限、依赖五类逐项检查。
4. 结论只能写“通过”“需修改”或“证据不足”，并留下具体原因。

另一个人或独立 Agent 的复核力度通常更高。只有同一人时，隔一段时间后在干净目录重跑命令可以发现部分问题，这仍属于自审，不能冒充独立审查。

### 5. 到里程碑才扩大范围

主流程通过后，才从下面四类需求中选一类进入下一轮：

- 覆盖更多输入和异常情况。
- 提升性能、可用性或稳定性。
- 补充权限、安全与发布检查。
- 增加第二条用户主路径。

每轮最多选择一类，并重新写范围和验收。出现以下信号时停止扩张，先回到上一步：核心测试不稳定、依赖没有降级方案、改动无法说明影响范围、审查没有可复现证据。

## 最后留下什么

一个可交接的最小项目包：

```text
README：运行前提、启动方式、已实现范围、未实现范围
tests/或验证记录：代表性输入、预期输出、实际结果
CHANGELOG：每次改动、影响范围、验证和遗留问题
风险表：关键依赖、失效信号和降级路径
复盘：计划与实际差异、一个可改变原因、下轮动作
```

项目结束或暂停时，用[阶段复盘与成果回流](../方法论/决策与项目/阶段复盘与成果回流.md)将原始证据、待研究问题、稳定方法和对外交付分别归档。

## 如何验收

| 检查项 | 通过条件 |
| --- | --- |
| 主流程 | 新环境按 README 可完成一次输入到输出 |
| 范围 | 已做和未做均已写明，未做项未被包装成已支持 |
| 可复现性 | 至少一组测试输入、预期和实际结果能对应 |
| 依赖 | 每项关键外部依赖都有失效信号和处理方案 |
| 审查 | 有交接包、审查结论和未解决问题 |
| 可维护性 | 下一位接手者能定位当前版本、改动和风险 |

## 常见失败与修正

| 失败表现 | 常见原因 | 修正动作 |
| --- | --- | --- |
| 功能越来越多，主流程仍不能用 | 先实现功能清单，后定义最小版本 | 冻结新增功能，只保留一条输入到输出链路 |
| “测试通过”却无法复现 | 没保存命令、数据或环境版本 | 将测试输入和实际输出放入交接包 |
| 依赖一断，项目停摆 | 把外部服务当成稳定基础设施 | 为关键依赖补本地样例、备用服务或停止条件 |
| 评审只看演示，没看边界 | 没有固定验收清单 | 按输入、输出、异常、权限、依赖五类复核 |
| 复盘只有感受，没有下轮动作 | 没有对照原始目标 | 先填计划与实际表，再提取一个可改变原因 |

## 什么时候不适用

- 涉及医疗、金融、隐私或安全关键系统时，必须加入领域规范、正式测试和合规审查，本页的轻量流程不够。
- 多团队、长期项目还需要接口协议、版本策略、需求管理、容量规划和明确责任分工。
- 主流程本身无法定义时，先回到[项目定义与验收](../方法论/决策与项目/项目定义与验收.md)，不要急于选技术栈。

- [GitHub：提交审查](https://docs.github.com/en/pull-requests/concepts/giving-reviews)：用于参考可追踪的审查结论与逐行评论流程。
