# K01 嵌入式实例

形式：**PC 可编译最小例**（已实际跑通）+ **SPL 对照片段**（未上板，未验证）。

## 一、PC 侧：已验证

文件：[hello.c](hello.c)（本目录）

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic hello.c -o hello.exe
```

实测（gcc 16.2.0，MSYS2 UCRT64，2026-09-30）：

```text
hello: sum=5 pin=5
```

无警告输出。这条命令同时完成四步中的编译、汇编与链接。

## 二、嵌入式侧：同样的四步，多出三样东西

交叉编译时命令换成了 `arm-none-eabi-gcc`，步骤仍是那四步，但有三处 PC 上没有的：

| 项目 | PC | STM32 |
| --- | --- | --- |
| 编译器 | `gcc`（生成 x86 代码） | `arm-none-eabi-gcc`（生成 ARM 代码，运行在本机、跑在板子上） |
| 入口 | `main` 就是起点 | `main` 之前还有启动文件：设栈顶、把 `.data` 从 Flash 拷到 RAM、把 `.bss` 清零 |
| 地址 | 由操作系统加载 | 由**链接脚本**决定代码和数据放在哪个地址 |

产物也多一步：链接出 `.elf` 后，再用 `objcopy` 转成 `.hex` 或 `.bin` 才能烧录。

> 本机未安装 `arm-none-eabi-*`（2026-09-30 核对 `command -v arm-none-eabi-gcc` 无结果），本节 ARM 侧命令**未验证**，只作流程对照。

## 三、SPL 对照：一个工程里有哪些文件

课程示例工程的最小构成（按 SPL 惯例，具体文件以课程工程为准）：

```text
startup_stm32f10x_md.s    启动文件：栈初始化、中断向量表
stm32f10x.h / system_stm32f10x.c   寄存器定义与时钟配置
stm32f10x_gpio.c / stm32f10x_rcc.c … 标准外设驱动（用到哪个编哪个）
main.c                     用户代码
```

与 PC 例子的对应关系：PC 侧只有 `hello.c` 一个源文件，嵌入式侧多出来的那几类文件，本质上都是「提供 `main` 运行所依赖的东西」——启动文件提供入口，驱动 `.c` 提供你调用的 `GPIO_Init` 等函数体。

这解释了嵌入式里最常见的一类链接错误：**调用了 `GPIO_Init` 但没把 `stm32f10x_gpio.c` 加进工程**，报的是 `undefined reference`，跟你在本机少编一个 `.c` 是同一回事。

## 四、把本知识点带回 PC 的做法

在没有板子的时候，用 PC 验证「多文件编译」这一步：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic main.c driver.c -o app.exe
```

少写其中一个 `.c`，就会看到 K01 易错清单里的 `undefined reference`。先在 PC 上把这个错认熟，将来在 Keil/VSCode 里遇到同一个报错就不会归错因。
