# 软件发布文件核对：选对文件并校验 SHA-256

项目和版本已经选定，下载页却有多个压缩包时，用一张卡把**目标环境、发布文件、官方摘要、本机摘要**对应起来。先回答「应该下载哪个」，再回答「下载到的是不是那一个」。

## 1. 从目标环境反查文件

准备目标机器的系统与架构、已选版本、项目官方入口。若文件是设备镜像，还要有整机型号、硬件修订版和厂商规定的镜像用途；只有芯片型号或系列名时，先停在待核。

1. 从官网或上游仓库打开带**具体版本号**的发布页。记下版本、链接和核对日期，避免下次打开滚动的 `latest` 时拿到另一版。
2. 对照该版文档核对系统、CPU 架构、文件用途和额外要求。需要在 Windows x64 上使用成品时，示意名称 `example-tool-2.4-windows-x64.zip` 是候选；同版的 `example-tool-2.4-linux-aarch64.tar.gz` 目标不同。两个名字均为虚构，实际含义要看发布说明。
3. 抄下上游标注的**完整文件名**，再去同一版本的官方索引或校验清单定位这一行。GitHub 发布页的 `Source code (zip)` 和 `Source code (tar.gz)` 是源码快照，内容与维护者挂出的成品附件可能不同；别仅凭扩展名选择。

## 2. 对下载完成的原文件算 SHA-256

下面是 Windows PowerShell 的读者示例。在下载目录打开终端，把示意文件名换成实际下载的名字。对**仍未解包的原文件**执行，别拿压缩包的摘要去比内部文件。

```powershell
Get-FileHash -LiteralPath '.\example-tool-2.4-windows-x64.zip' -Algorithm SHA256
```

它返回 `Algorithm`、`Hash` 和 `Path`。先核对路径，再对照发布方给的 由 64 个十六进制字符组成的摘要，逐位比较全部字符，大小写可忽略。如果浏览器给文件加了 `(1)`，选择本地实际文件来算，并保留原发布文件名用于定位官方那一行。只有 **文件适用条件已核对、摘要来源可信、两个摘要一致**，才记为「文件核对通过」。

| 遇到什么 | 下一步 |
| --- | --- |
| 找不到同版本、同文件的官方摘要 | 记「未核对」；向发布方查找清单或其文档指定的其他验证方式。别用镜像站评论补值。 |
| 摘要不一致 | 暂停解包和运行，回查是否选错版本、文件、算法或下载未完成；重新从可信入口下载后再比。 |
| 摘要一致，但系统、架构或镜像用途不符 | 仍然停止；你拿到了这份文件，但它不适用于当前目标。 |
| 上游提供签名或签名清单 | 按项目文档使用独立可信渠道确认的发布公钥或指纹，核对签名实际覆盖的文件。签名失败、密钥身份未确认或覆盖对象不明时，不记为通过。 |

SHA-256 对照的是文件内容与参考摘要。如果附件和摘要都来自同一个被替换的页面，两者仍可能吻合。用可信发布密钥核对签名，可以为签名覆盖的内容补上来源证据；它仍不能证明文件没有漏洞、能在你的机器运行，或适合某块设备。官方的签名流程存在时，按该流程处理。

## 3. 留一张能重查的下载卡

```text
准备做什么 / 目标系统与架构（设备镜像另填型号、修订版和用途）：
上游发布页 / 固定版本 / 核对日期：
发布文件全名 / 附件链接：
官方摘要来源链接 / 期望 SHA-256 / 本机 SHA-256：
签名覆盖对象与状态：通过 / 失败 / 未提供 / 未核
决定：文件核对通过 / 暂停；缺项与下一步：
```

交给另一位读者时，对方应能回到**同一版本**、找到**同一文件记录**，并解释为何选它、比的是哪个摘要。换了版本、附件或目标环境，就重查对应项。这张卡记录到文件核对为止，安装和运行结果另记。
