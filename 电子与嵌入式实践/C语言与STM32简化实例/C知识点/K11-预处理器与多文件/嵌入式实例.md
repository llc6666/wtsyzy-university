# K11 嵌入式实例

形式：**PC 多文件工程**（已编译运行）+ **SPL 工程组织对照**（未上板，未验证）。

## 一、PC 侧：已验证

目录 [multifile-demo/](multifile-demo/)，三个文件。

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic main.c sensor.c -o app.exe
```

实测输出（gcc 16.2.0，2026-10-01）：

```text
1) 读到数值：2468
2) 读取次数（来自另一个文件的全局变量）：3
3) 传空指针的返回值：-1（非 0 表示失败）
```

分开编译再链接（等价的另一种做法）：

```bash
gcc -std=c17 -c main.c   -o main.o
gcc -std=c17 -c sensor.c -o sensor.o
gcc main.o sensor.o -o app.exe
```

另外验证过：从别的文件引用 `sensor.c` 里的 `static` 变量，链接失败（退出码非 0）。

## 二、SPL 工程对照：文件怎么分

标准库工程大致是这个形状（以实际工程为准）：

```text
main.c                      用户程序
led.c / led.h               自己写的驱动模块（一个外设一对文件）
stm32f10x_gpio.c            库提供的驱动实现
stm32f10x.h                 寄存器定义与外设结构体
system_stm32f10x.c          时钟与系统初始化
startup_stm32f10x_md.s      启动文件
```

对照本知识点的示例工程：

| 示例工程 | SPL 工程 |
| --- | --- |
| `sensor.h` | `led.h`（对外声明） |
| `sensor.c` | `led.c`（实现，内部辅助函数 static） |
| `main.c` | `main.c` |
| 手动 gcc 编译链接 | IDE/工具链按工程文件列表编译链接 |

**模块化方式完全一样**：一个外设一对 `.c/.h`，头文件只放声明。

## 三、`stm32f10x.h` 里有什么

这个头文件是本知识点最好的反面教材兼正面教材——它很大，但组织原则就三条：

1. **寄存器映射**：把外设寄存器包成结构体指针（K07/K08 的内容）
2. **条件编译选芯片**：用 `#ifdef STM32F10X_MD` 之类决定包含哪些定义
3. **大量宏**：寄存器位、标志、参数选项都定义成宏

读它的方式：不要从头读到尾，用「跳转到定义」看某一个具体外设（例如搜 `GPIO_TypeDef`、`GPIO_Pin_5`）。

## 四、条件编译的嵌入式用法

```c
#define USE_UART_DEBUG 1

#if USE_UART_DEBUG
    #define DEBUG_PRINT(fmt, ...) printf(fmt, ##__VA_ARGS__)
#else
    #define DEBUG_PRINT(fmt, ...) ((void)0)   /* 发布时完全消失 */
#endif
```

这样调试打印在发布版本里不占空间也不耗时间——MCU 的 Flash 与运行时间都很宝贵。

## 五、把本知识点带回 PC 的做法

驱动模块先在 PC 上按「头文件 + 实现 + 主程序」写好，用 gcc 编译验证接口，再搬到 MCU 工程里。这样到了 Keil/VSCode 里只需要处理工具链配置，不必同时调试接口设计。

（编译多个文件时，如果 IDE 报「undefined reference」，回想 K01 的易错清单第 2 条：声明有、定义没有，或链接时漏了某个 `.c`。）
