# S03 串口收发与命令解析

## 一句话结论

**串口编程的标准结构是：中断只往环形缓冲里写一个字节，主循环从缓冲里取、攒成一行、再解析。** 中断不做解析，主循环不做等待。

## 实测（PC 模拟）

文件：[uart-ringbuf-demo.c](uart-ringbuf-demo.c)

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic uart-ringbuf-demo.c -o uart-ringbuf-demo.exe
```

```text
[主循环] 收到一行：LED ON
  -> 执行：开灯
[主循环] 收到一行：PWM 60
  -> 执行：PWM 占空比 60%
[主循环] 收到一行：LED OFF
  -> 执行：关灯

[突发] 模拟主循环正忙时，中断连续收到 20 字节：
  缓冲内积压 16 字节，已丢弃 4 个
  主循环腾出手后读出 16 字节，剩余 0 字节
```

**20 字节突发、容量 16、丢弃 4 个**——这段演示的是缓冲容量不足时的真实后果：数据静默丢失，不报错。

这里的 PC 程序把“中断写入”和“主循环读取”按先写后读顺序模拟，验证的是环形缓冲的边界与协议解析。它没有模拟真实 CPU 上的并发抢占，因此不能单凭这段程序证明中断与主循环之间的共享索引已经具备原子性；上板时还要按 MCU 位宽、访问顺序和临界区策略复核。

## 一、为什么必须用缓冲

串口一个字节一个字节地来，两个字节之间的间隔由波特率决定。如果主循环正在做别的事，来的字节就会丢。

对比三种写法：

| 写法 | 问题 |
| --- | --- |
| 主循环里死等一个字节 | 期间什么都做不了，其他任务全停 |
| 中断里直接解析整条命令 | ISR 太长，且命令没到齐时状态难维护 |
| **中断写缓冲，主循环解析** | 推荐：职责清楚，两边都不阻塞 |

## 二、缓冲容量怎么定

按**最坏情况的突发量**定，不是按平均速率：

```text
最坏突发量 = 主循环最忙时段 × 波特率对应的字节率
```

上例中 20 字节突发、16 字节容量 → 丢 4 个。若主循环最长会有 50ms 无法读缓冲，115200 波特率下每毫秒约 11.5 字节，就需要约 600 字节的缓冲——比直觉大得多。

（真实工程还要考虑：丢了的字节不会补回来，所以关键数据要靠协议层的校验与重传来兜底。）

## 三、攒行与 `\0`

```c
if (b == '\n') {
    line[line_len] = '\0';      /* 补结尾，才能当字符串用 */
    execute(line);
    line_len = 0;
} else if (line_len + 1 < LINE_MAX) {
    line[line_len++] = (char)b; /* 永远留一个字节给 \0 */
}
```

`line_len + 1 < LINE_MAX` 这一句是 K05 的核心规则：**永远给 `\0` 留一个字节**。

## 四、解析：比较用 `strcmp`，不是 `==`

```c
if (strcmp(line, "LED ON") == 0) { /* 对 */ }
if (line == "LED ON")             { /* 错：比的是地址 */ }
```

带参数的命令用 `sscanf` 或自己解析：

```c
if (strncmp(line, "PWM ", 4) == 0) {
    int duty = 0;
    if (sscanf(line + 4, "%d", &duty) == 1) { /* 用 duty */ }
}
```
