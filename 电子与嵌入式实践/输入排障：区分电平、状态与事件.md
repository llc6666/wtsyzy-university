# 嵌入式输入排障：区分电平、状态与事件

## 适用场景

程序能编译、LED 或蜂鸣器也能部分动作，但出现下面任一种现象时使用本流程：

- 按键计数不动、一次按键计数两次或按住持续增加。
- 传感器输出能驱动执行器，却统计不到正确的进入/离开次数。
- 输入方向记反，遮挡和移开、按下和松开的业务含义颠倒。
- 改了代码却没有效果，实际编译的工程文件不是刚修改的文件。
- `0 Error(s)`，但板上功能仍不正确。

这类问题通常不是某一个 `if` 写错这么简单，而是把五种不同对象混在了一起：输入当前电平、上次采样电平、确认后的稳定状态、边沿事件、输出或计数结果。

## 先建立五列信号表

开始改代码前，为每个输入和输出填一行。不要用“高电平就是按下”这样的记忆代替测量。

| 对象 | 记录什么 | 典型问题 |
| --- | --- | --- |
| 当前输入电平 | 这一次从 GPIO 输入寄存器读到的值 | 把输入寄存器读成输出寄存器 |
| 上次采样值 | 用于和当前值比较的历史样本 | 多个引脚共用一个状态变量 |
| 稳定状态 | 经过消抖或稳定窗口确认后的业务状态 | 把一个采样变化当成一次有效事件 |
| 边沿事件 | 例如“松开→按下”或“无遮挡→遮挡” | 方向守卫写反，或事件触发后没有更新历史样本 |
| 输出/计数 | LED、蜂鸣器、计数器等动作结果 | 让输出函数顺便修改计数，重复调用就重复计数 |

再补充三列硬件事实：引脚、输入有效电平、输出有效电平。输入的有效电平与输出的有效电平可以不同，必须分别记录。

## 一、先确认读的是输入数据

外部按键、红外、光敏模块的当前状态，必须从芯片规定的输入数据通道读取。以 STM32F1 为例，RM0008 将 `GPIOx_IDR` 定义为端口输入数据寄存器，将 `GPIOx_ODR` 定义为端口输出数据寄存器；二者承担的含义不同。

```c
/* 伪代码：具体函数按 HAL、SPL 或寄存器工程的接口替换。 */
bool current = read_gpio_input(input_port, input_pin);
```

故障排查时逐项确认：

1. GPIO 模式是输入、上拉、下拉还是复用功能。
2. 读取函数或寄存器确实对应输入数据，而不是输出锁存值。
3. 万用表或逻辑分析仪测的是目标引脚，不是模块的电源、指示灯或其他引脚。
4. 模块与主控共地，输入电压处在芯片允许范围内。
5. 记录松开/按下、无遮挡/遮挡、空闲/触发时的真实电平。

如果输入电平事实没有确认，先停止修改计数逻辑。代码中的 `!input` 只能表达电平取反，不能证明“取反后就是业务上的遮挡”或“低电平就是按下”。

## 二、初始化时从硬件采样历史值

边沿检测依赖“上一次值”和“这一次值”。初始化 GPIO 后先采一次真实输入，作为历史基准：

```c
static bool previous_input;

void input_init(void)
{
    configure_gpio_input();
    previous_input = read_gpio_input();
}
```

这样可以定义开机策略：如果设备上电时按键已经按下，是忽略这次持续按住，还是稳定确认后产生一次事件。两种策略都可以，但必须写进验收表。把历史值硬编码为 `1`，等于假设上电瞬间输入一定处于某种状态，容易产生开机误计数。

## 三、把“状态跟随”和“边沿事件”拆开

同一个输入可能同时驱动两个不同任务：

- **状态跟随型**：蜂鸣器在当前触发状态下保持响，输入恢复后停止。它关心现在是什么状态，动作应当幂等。
- **边沿事件型**：只在“未触发→触发”时把计数加一。它关心发生了哪一个方向的变化。

不要用一个条件同时控制两种任务。推荐先采样，再分别处理：

```c
bool current = read_gpio_input();
bool changed = current != previous_input;

if (changed) {
    if (is_enter_edge(previous_input, current)) {
        event_count++;
    }
    previous_input = current; /* 变化就更新记忆，与方向无关 */
}

follow_output(current);       /* 只跟随当前状态，不修改 event_count */
```

这里的 `is_enter_edge` 必须由输入极性表定义。若遮挡对应高电平，进入遮挡可能是 `0→1`；若遮挡对应低电平，进入遮挡则是 `1→0`。不能从变量名或上一块代码的方向判断中猜出来。

## 四、事件判定与历史更新不能绑死

一个很隐蔽的错误是把历史更新放在方向条件内部：

```c
if (changed) {
    if (previous_input == RELEASED) {
        count++;
        toggle_led();
        previous_input = current;
    }
}
```

当变化方向相反时，`previous_input` 不更新，下一轮仍拿旧值比较，后续按键可能永久失效。正确结构是：

```c
if (changed) {
    if (is_press_edge(previous_input, current)) {
        count++;
        toggle_led();
    }
    previous_input = current;
}
```

记忆更新回答“下一轮从哪里比较”；事件判断回答“这一次要不要动作”。两者职责不同，不能让事件未成立时阻止记忆前进。

## 五、采样、消抖和任务调度要各有负责人

“每隔 20ms 检查一次”只描述了采样节奏，不能自动证明消抖成功，也不能保证每个任务 20ms 内响应。将职责写成任务表：

| 任务 | 负责什么 | 不负责什么 |
| --- | --- | --- |
| GPIO 采样 | 在规定周期读取一次当前电平 | 不直接决定业务事件 |
| 消抖状态机 | 由候选状态和稳定时间确认状态变化 | 不补造没有采到的历史电平 |
| 事件判定 | 根据稳定状态的方向生成一次事件 | 不负责显示和蜂鸣器输出 |
| 状态输出 | 让输出跟随当前确认状态 | 不修改事件计数 |
| 显示刷新 | 低频展示计数和状态 | 不承担输入采样 |

非阻塞主循环的时基和“错过周期”的处理，见[非阻塞主循环：到期检查、按键消抖与任务验收](非阻塞主循环：到期检查、按键消抖与任务验收.md)。若 OLED、串口或通信函数可能长时间阻塞，应测量最长执行时间；否则输入任务的实际采样间隔会被拉长。

## 六、`volatile` 只能解决一类问题

如果变量由中断或硬件异步改变，可能需要 `volatile` 访问限定；但它不能完成以下工作：

- 不能把一个电平变化自动变成一次业务事件。
- 不能决定按下/松开的方向。
- 不能替代消抖、原子性、锁或事件队列。
- 不能证明主循环读取的是正确 GPIO 通道。

GCC 官方文档也明确说明，`volatile` 主要约束易变对象的访问，不能作为普通内存写入顺序的通用屏障。已有[volatile 与编译器优化](C语言与STM32简化实例/C知识点/K10-volatile与编译器优化/README.md)页面可用于复习；本页只把它放在输入排障的证据链中，不重复展开。

## 七、按证据层次定位，不把编译通过当功能通过

每次修复至少留下三层记录：

### 1. 源码层

- 输入读取函数与引脚配置对应。
- 变量名只表达一种物理或业务含义。
- 事件计数不藏在输出函数内部。
- 记忆值在每次有效采样变化后都会更新。
- 时间戳、消抖窗口和显示刷新各自只有一个负责人。

### 2. 构建层

- 修改的源文件确实出现在 IDE 工程树或构建清单中。
- 全量构建，而不是只编译一个入口文件。
- 读取构建日志，确认修改文件确实重新编译。
- 检查目标文件时间戳，避免运行旧的 `.o`、`.axf` 或 `.hex`。

### 3. 硬件层

- 上电不操作，输入不会凭空产生事件。
- 快速连续按压若干次，计数与事件次数一致。
- 按住不放，计数不持续增加，状态输出可以保持。
- 上电时已按住，行为符合事先定义的启动策略。
- 触发和解除触发分别测试，确认事件方向没有反。
- 输入极性、输出有效电平和测量点写入记录。

只有三层证据都对应，才可以写“功能通过”。“0 Error(s)”只能证明某次构建没有报告错误，不能证明输入链路、事件方向或烧录产物正确。

## 常见错误速查

| 现象 | 优先检查 |
| --- | --- |
| 输入永远不变 | IDR/ODR、GPIO 模式、测量点、共地 |
| 第一次上电就多一次 | 历史值是否从硬件采样，启动按住策略是否定义 |
| 第一次能用，第二次失效 | 反方向变化时历史值是否仍更新 |
| 按住持续计数 | 事件是否误写成当前电平，输出函数是否修改计数 |
| 触发和解除方向反了 | 实测极性、旧值与当前值的方向表 |
| 编译成功但功能没变化 | 工程文件是否纳入、全量构建、目标产物和烧录版本 |
| 状态输出正确但计数错误 | 跟随状态与边沿事件是否使用了不同判断 |
