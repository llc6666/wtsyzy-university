# 嵌入式工程排障：区分工程树、搜索路径与硬件证据

## 适用场景

当你遇到下面的现象时，先用本页拆分问题层次：

- 编辑器显示大量红色波浪线，但 Keil 构建日志没有对应错误。
- 工程左侧能看到某个头文件，编译器却报告 cannot open source input file。
- 头文件已经找到，链接阶段仍出现 Undefined symbol。
- 构建显示 0 Error(s)，下载后外设仍没有预期动作。

这些现象经常被归为“路径错了”，但至少涉及工程成员、头文件搜索、宏和编译器版本、链接输入、下载产物、芯片接线六个层次。先区分层次，再改配置。

## 四个系统分别回答什么问题

| 系统 | 它回答的问题 | 不能替代的证据 |
| --- | --- | --- |
| 工程树或 Target 成员 | 哪些 .c/.cpp/.s 文件属于当前构建目标 | 不能自动证明头文件搜索路径正确 |
| 编译器 Include Paths | #include 失败时到哪些目录寻找头文件 | 不能证明实现文件已加入 Target |
| 编辑器 IntelliSense | 当前编辑器按自己的配置如何解析代码 | 不能直接证明 Keil 构建失败 |
| 下载与硬件 | 哪个产物被烧录、芯片和接线是否匹配、现象是否正确 | 不能由编辑器颜色或 0 Error 推出 |

Keil 的 Target 选项包含 C/C++、链接器、输出和调试等配置；其中头文件搜索目录和当前 Target 的源文件成员需要分别核对。VS Code 的 IntelliSense 也有自己的 includePath、宏和编译器配置，除非使用编译数据库或配置提供程序，否则它不会自动继承另一个 IDE 的全部设置。

## 从错误文本开始分流

### 1. 找不到头文件

先确认三件事：

1. 文件确实存在，文件名、大小写和后缀正确。
2. #include 的写法与目录配置一致，例如 #include "motor.h" 要求对应目录出现在搜索路径中，#include "Hardware/motor.h" 则依赖工程根目录和相对路径的稳定关系。
3. 当前构建的 Target 采用了你检查过的 Include Paths，而不是另一个 Target 或文件级覆盖配置。

不要因为工程树显示了 Hardware/motor.h，就认为编译器一定能找到它。工程树是文件组织视图，搜索路径是编译命令的一部分。

### 2. 找不到函数或变量定义

这类问题通常已经越过头文件搜索阶段，应检查：

- 声明所在头文件是否被正确包含。
- 实现文件是否加入当前 Target 并真正参加本次编译。
- 函数声明、定义和调用的参数、返回类型、命名空间或链接属性是否一致。
- Build Output 中是编译错误，还是链接器报告的 Undefined symbol。

只把 .c 文件拖进工程树不等于它已加入当前 Target。可以从完整 Build Output、目标文件更新时间和链接器输出共同确认。

### 3. 编辑器错误与构建结果冲突

编辑器提示只代表当前 IntelliSense 配置下的解析结果。逐项核对 compilerPath、includePath、宏定义和 compile_commands.json；再用真实构建命令判断编译器结果。两套诊断可以分别正确，也可以一套过期，不能互相替代。

### 4. 构建成功但板上不工作

按证据链继续向后检查：

1. 生成的 HEX/AXF 是否来自刚才的 Target 和源码版本。
2. 下载器是否把这个产物写入目标芯片，下载日志是否有校验结果。
3. 芯片型号、时钟、引脚复用、供电、共地和外设有效电平是否与板卡资料一致。
4. 是否用万用表、逻辑分析仪、串口日志或示波器观察了目标信号。

0 Error(s) 只能证明某一轮构建没有报告错误，不能证明下载对象、接线和外设行为正确。

## 一次排障应留下的产物

不要只保存“改好了”的结论，至少留下以下记录：

| 产物 | 最低内容 |
| --- | --- |
| 文件关系表 | 源文件、头文件、所属 Target、实现接口 |
| 配置快照 | Include Paths、宏、编译器版本、链接选项 |
| 构建日志 | 完整错误文本、构建时间、Target 名称和退出结果 |
| 产物对应表 | 源码提交、AXF/HEX 生成时间、下载时间 |
| 硬件观察表 | 测试接线、输入条件、测量点、预期与实际现象 |

修改时一次只变一个层次：先修路径，重新构建；再修 Target 成员，重新构建；最后才进入下载和硬件排查。这样能避免把多个变化的结果混在一起。

## 常见失败与修正

| 错误做法 | 为什么不可靠 | 修正动作 |
| --- | --- | --- |
| 看到工程树有文件就认为能 #include | 文件视图与编译器搜索路径是不同配置 | 查看当前 Target 的 Include Paths 和实际编译命令 |
| 把 VS Code 红线当成 Keil 错误 | 两者可能使用不同宏、头文件目录和编译器 | 分别保存 IntelliSense 诊断和真实 Build Output |
| 只把头文件加入工程 | 头文件声明不提供函数实现 | 将实现文件加入当前 Target，并检查链接输入 |
| 看到 0 Error(s) 就宣布硬件成功 | 构建没有覆盖下载、芯片、接线和信号 | 用产物对应表和测量记录完成后续验收 |
| 为了消除红线递归加入大量目录 | 可能掩盖错误包含并拖慢解析 | 只加入实际依赖目录，优先使用编译数据库或精确配置 |
