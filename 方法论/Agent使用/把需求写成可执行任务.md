# 把需求写成可执行任务

## 何时用

准备让 Agent 写代码、整理资料、调研、改文件、制作报告或发布内容时使用。它解决“Agent 做了很多，却没做对”的问题。

## 输入

- 你要解决的一个具体问题。
- 现有资料、目标目录或可访问系统。
- 不可触碰的边界。
- 判断完成的标准。

## 步骤

### 1. 用一句话限定任务

句式：`在 [范围] 内，为 [使用者] 完成 [可检查交付物]，解决 [具体问题]，并以 [验收方式] 判断完成。`

例：`在公开笔记目录内，为首次使用者完成一份来源卡模板，以链接检查通过、无个人信息、可按模板创建一张卡片作为验收。`

“帮我整理一下”“把它做好”“研究这个方向”都缺少范围和验收，先不要执行。

### 2. 填任务契约

复制模板。方括号未填完时，任务状态是“待澄清”。

```markdown
# 任务契约

## 目标
- 要解决的问题：
- 交付物：
- 使用者：

## 来源与范围
- 可读取：
- 禁止读取：
- 可编辑：
- 禁止编辑：

## 行动权限
- 可直接执行：
- 执行前展示方案：
- 必须人工确认：

## 验收
- 功能/内容：
- 独立检查：
- 隐私与版权：

## 停止条件
- [待填写]
```

### 3. 把大目标切成可验证阶段

每阶段都要有输入、动作、产物和检查点。

| 阶段 | 输入 | Agent 动作 | 产物 | 检查点 |
| --- | --- | --- | --- | --- |
| 审计 | 文件/来源 | 列出候选和风险 | 选取清单 | 范围是否正确 |
| 实施 | 已确认清单 | 最小修改 | 草稿或补丁 | 是否满足目标 |
| 验证 | 草稿/补丁 | 独立检查 | 测试记录 | 是否可交付 |
| 交接 | 已验证结果 | 记录状态 | 交接卡 | 他人能否接手 |

### 4. 在提示中写出“先问再做”的条件

明确写：`当目标、范围、路径、权限或验收任一项不清楚时，先列出缺失项，停止写入和外部操作。`

这条规则比堆叠角色设定有效，因为它直接约束了下一步动作。

## 可复制提示词

```text
你要完成的任务：{一句话目标}

交付物：{文件/表格/代码/报告及位置}
可读取范围：{目录、链接、资料}
可编辑范围：{目录、文件}
禁止事项：{隐私、删除、外部发布、无来源推断}
行动权限：{可直接做 / 先展示 / 必须确认}
验收方式：{测试、链接、抽查、来源核验}
停止条件：{什么情况必须向我提问}

开始前先复述：目标、范围、风险、计划和验收。
任何一项不清楚时，只列出待确认问题，不执行写入或外部动作。
结束时给出：变更清单、验证结果、未解决风险、下一步。
```

## 交付物

- 一句可验收的目标。
- 一张已填的任务契约。
- 按阶段拆分的执行计划。

## 验收

- 交付物能被打开、运行、审阅或量化检查。
- 可读取和可编辑范围使用明确路径、来源或系统名称。
- 至少写出一个停止条件。
- 第三方读任务契约后，无需猜测 Agent 能否发布、删除或访问敏感资料。

## 常见失败与修正

- 目标只写“优化”：改为目标指标、对象和验收测试。
- 允许“自行处理”：改为列出允许的动作与禁止项。
- 一次要求读取整个电脑：先列候选目录和文件类型，按需扩展。
- 只规定格式不规定事实来源：为每个结论指定来源等级和复查日期。
