# Wi-Fi 已连接却用不了：从无线链路查到应用

设备显示已连接，但网页打不开、局域网设备访问不到，或应用请求超时。先选一个明确失败的动作，按「无线连接 → IP 配置与路径 → 名称解析 → 目标服务」逐项记录。每一步都写清观察到了什么，再决定下一步查哪里。这里是排查顺序；DNS 本身也是网络上的应用协议。

## 先固定要访问的目标

准备一台出现问题的设备，以及一个明确的目标，例如自己管理的局域网控制页，或本来可访问的 HTTPS 服务。记下原始报错、时间、使用的网络接口、服务名称及文档注明的端口。有线上网、手机数据或 VPN 也在工作时，先记录这些并行路径；不要把其他接口上的成功算成 Wi-Fi 的证据。

先回答：**我需要访问局域网设备，还是需要访问公网？** 局域网服务能用就可能已满足任务；“无 Internet”图标在这个场景中不等于故障。

## 按层记录，找到第一处缺口

| 检查顺序 | 看哪里、记什么 | 这一项通过仍不能说明什么 |
| --- | --- | --- |
| 1. 无线链路 | 在系统中核对无线接口的连接状态、是否连到预期网络、是否反复掉线。普通基础设施 Wi-Fi 中，终端（STA）接入接入点（AP）。802.11 的无线物理层（PHY）和介质访问控制（MAC）处理无线信号传输及链路通信。[IEEE 802.11 工作组](https://www.ieee802.org/11/abt80211.html) | 已接入说明终端建立了这一段无线连接，不能证明已取得可用 IP、外网可达或应用正常。同名 SSID 也不能证明两台设备在同一个可互访的网络里。 |
| 2. IP 与路径 | 对着**正在使用的接口**记录地址、前缀或子网掩码、网关。对于外网目标，再确认有没有匹配的路由；对同子网目标，通常不需经过默认网关。自动配置的 IPv4 网络可检查 DHCP 是否提供了预期地址和参数。[RFC 1122](https://www.rfc-editor.org/rfc/rfc1122.html) · [RFC 2131](https://www.rfc-editor.org/rfc/rfc2131.html) | 有地址或有网关条目，不能证明目的地址可达。接入点与默认网关是两种角色，家用设备可兼任。 |
| 3. 名称解析 | 目标使用域名时，记下查询的**同一个名称**，区分返回地址、名称不存在、查询超时等结果。拿到地址后，还需确认该结果符合预期。[RFC 1034](https://www.rfc-editor.org/rfc/rfc1034.html) | DNS 查询成功不能证明目标端口可达；应用也可能使用不同于系统查询工具的解析方式。目标已直接使用 IP 时可跳过此项。 |
| 4. 目标服务 | 对已知且有权访问的目标，看清应用使用的是 TCP 还是 UDP。对于 TCP，先区分端口连接失败与已经收到服务响应，再看 TLS、登录或业务错误。UDP 依据应用自己的请求和响应记录判断。 | TCP 端口能连接，不等于 TLS、身份认证和业务请求成功；TCP 探测也不能说明 UDP 状态。 |

**停止线：**第一处缺证据时，先在该处缩小范围。无线状态反复断开，就先记录断开时间和接入条件；无线稳定但 IPv4 地址与预期不符，就先核对地址来源。若几层的记录都正常而只有一个应用失败，转到该应用的协议、服务状态和日志，不先重置整个网络。

## Windows 上可直接查看的项目

以下是给读者的检查步骤，只在自己的设备和有权访问的服务上使用。先到 Windows 网络设置查看当前 Wi-Fi，也可以在 PowerShell 读取接口和地址信息：

```powershell
netsh wlan show interfaces
ipconfig /all
```

第一条找正在用的无线接口及其连接状态；第二条在同一个接口段找地址、掩码、默认网关、是否启用 DHCP 和 DNS 服务器。虚拟网卡或断开的网卡信息不要混入。如果接口信息无法读取，记下权限或系统提示，改看系统网络设置。发给别人前先脱敏，尤其是实际 SSID、MAC 地址、主机名及内部网段。

如果前两步已有记录，再选与故障相关的一条：

```powershell
Resolve-DnsName -Name (Read-Host '输入失败请求中的主机名，不含 https:// 或路径') -DnsOnly
```

```powershell
$target = Read-Host '输入已知且有权访问的主机名或 IP'
$port = [int](Read-Host '输入该服务文档中的 TCP 端口')
Test-NetConnection -ComputerName $target -Port $port -InformationLevel Detailed
```

端口检查读 `TcpTestSucceeded`，并核对 `InterfaceAlias` 和 `SourceAddress`，避免 VPN 或有线网卡替 Wi-Fi 完成连接。若输入主机名，失败还可能发生在解析阶段；如有从服务管理方确认的 IP，可在**保持服务和端口一致**的前提下单独检查 TCP。浏览器中把 HTTPS 域名直接换成 IP 可能改变证书校验和站点选择，不适合拿来直接判定 DNS 故障。

文档入口：[Windows 无线排障](https://learn.microsoft.com/en-us/troubleshoot/windows-client/networking/wireless-network-connectivity-issues-troubleshooting) · [ipconfig](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/ipconfig) · [Resolve-DnsName](https://learn.microsoft.com/en-us/powershell/module/dnsclient/resolve-dnsname) · [Test-NetConnection](https://learn.microsoft.com/en-us/powershell/module/nettcpip/test-netconnection)。

## 两个可以照着写的判断

| 已知观察（示意，非实测） | 下一步 | 暂时不能下的结论 |
| --- | --- | --- |
| 终端在预期 Wi-Fi 上；用确认过的地址能够连接某一服务的 TCP 端口，但同一服务使用的域名查询超时。 | 检查当时使用的解析器和查询的名称；补记应用是否使用同一个解析路径。 | 不能据此认定“全网 DNS 挂了”，也不能认为网站业务已正常。 |
| DNS 返回预期地址，目标 TCP 端口连通，浏览器却报告证书错误。 | 记录证书报错类别、访问的域名及系统时间等条件，再查 TLS；不要关闭证书校验。 | 不能凭 TCP 成功认定 HTTPS 已通过，也不应继续把问题归到无线信号。 |

不要把 `ping` 当成必经关卡：它能反映目标对这次 ICMP 探测的响应，不能代替 TCP 端口或应用请求。目标也可能不回复 ICMP，因此不回包不等于目标服务不可用。

## 交付物与验收

留下一张能交给另一位同学的记录卡，说明「哪一步出现了什么证据、下次只补哪一项」。没有看过的字段写「未查」，不要写「正常」。

```text
设备及时间：
失败动作、目标服务与原始报错：
该目标只需局域网，还是需要公网：
无线接口和连接状态：
该接口地址、前缀、网关与已知路径：
目标名称解析结果（若适用）：
TCP 端口或应用响应（若适用）：
第一处缺口：
下一步只做哪一项检查：
```

验收时，用记录卡解释为什么下一步只查某一层，同时指出一条当前证据不支持的结论。需要连续多次观察的间歇故障，应分开记录成功与失败的时间和接口，不用某一时刻通畅覆盖其他失败记录。

## 来源与适用边界

本页把本地背景阅读笔记中的分层练习改写为普通客户端排查卡。官方 802.11 概览用于界定 MAC/PHY；RFC 仅作为分层、IPv4 DHCP 和 DNS 的基础入口，具体协议的后续更新以官方索引为准。Windows 示例按官方命令说明整理，未在设备上执行。来源未提供运行验证记录；本轮仅整理，未执行测试。示意情境不代表真实网络测量。

本文适用于基本客户端连通性定位；企业认证、IPv6 地址配置、无线漫游和 Mesh 多跳需要另外核对各自的机制、版本及现场证据，不能用本卡的一条连通记录判定整个网络正常。
