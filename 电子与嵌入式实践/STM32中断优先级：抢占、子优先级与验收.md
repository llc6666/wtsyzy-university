# STM32 中断优先级：抢占、子优先级与验收

## 这页解决什么问题

中断优先级真正影响的是“谁能打断谁”和“同时挂起时谁先得到处理”。只会填写 CubeMX 的优先级数字，不足以证明中断设计正确。需要同时理解优先级分组、抢占优先级、子优先级、服务时间和标志清除。

## 1. 两个优先级维度

- **抢占优先级**：数值更小的中断可以打断正在执行的数值更大的中断，前提是分组提供了抢占位。
- **子优先级**：抢占优先级相同而多个中断处于等待状态时，用来决定处理顺序；它不能让一个同级中断打断另一个正在执行的同级中断。

Cortex-M 的优先级寄存器位数和实现有关，STM32 不同系列、库版本和配置方式也可能不同。先选优先级分组，再按任务紧急程度分配数字；不要拿别的芯片或旧库的分组表直接套用。

## 2. 配置的最小顺序

在 HAL 工程中，典型结构如下：

```c
/* 具体分组和 IRQ 名称以当前系列的 HAL/CMSIS 头文件为准 */
HAL_NVIC_SetPriorityGrouping(NVIC_PRIORITYGROUP_2);

HAL_NVIC_SetPriority(USART1_IRQn, 2U, 0U);
HAL_NVIC_EnableIRQ(USART1_IRQn);
```

优先级分组应由系统统一决定，并在初始化阶段集中设置。给单个中断设置优先级时，确认抢占参数、子优先级参数、IRQ 通道和外设句柄属于同一工程。配置完成后还要检查对应的 IRQ 入口是否调用了 HAL 处理函数，标志是否被清除，回调是否真的被触发。

## 3. 用任务需求分配优先级

先写“延迟超过多少会出问题”，再分级。一个仅供说明的表格如下：

| 事件 | 可能的处理策略 | 需要观察的证据 |
| --- | --- | --- |
| 必须尽快关闭输出的保护事件 | 较高抢占优先级，服务函数极短 | 触发到输出关闭的时间、波形和故障记录 |
| 定时采样或控制节拍 | 中等抢占优先级，固定上限的执行时间 | 周期抖动、丢样本和 ISR 时长 |
| 串口接收 | 根据缓存和协议容忍度安排 | 接收计数、溢出计数、帧完整性 |
| 显示刷新和调试日志 | 较低优先级或放到主循环 | 是否阻塞关键事件 |

表中的“高/中/低”是需求关系，不是固定数字。只有测得执行时间和丢失后果，数字才有意义。

## 4. 中断服务函数的硬边界

中断服务函数里优先做四件事：确认来源、读取必要数据、清除或交给 HAL 清除标志、写入最小事件记录。以下动作应谨慎处理：

- 长循环和 `HAL_Delay`；
- 阻塞式串口发送和 `printf`；
- 大量浮点计算、动态内存分配和复杂协议解析；
- 未加保护就与主循环共享多字节状态。

常见结构是“中断采集，主循环处理”：中断只写固定大小的环形缓冲区或事件队列，主循环再完成日志、显示和协议解析。共享变量需要明确 `volatile`、原子性和并发保护条件；`volatile` 本身不等于互斥锁。

## 5. 可复现验收

为每个中断建立最小测试，而不是只观察“偶尔能进回调”：

1. 给事件一个明确触发源，例如按键、定时器或串口字节。
2. 在入口和出口翻转一个测试 GPIO，测量服务时间和嵌套关系。
3. 人为提高触发频率，记录丢失、溢出、重复和延迟。
4. 同时触发两个中断，验证抢占优先级和子优先级符合设计。
5. 复位、冷启动和异常恢复各测试多次，保存波形、计数和工程提交号。

验收记录至少包含：优先级分组、每个 IRQ 的两级参数、触发源、服务时间、共享数据、标志清除位置和未解决风险。

## 6. 常见错误

| 错误 | 为什么危险 | 修复 |
| --- | --- | --- |
| 以为数字越大优先级越高 | 可能把关键事件放到低优先级 | 先查当前 CMSIS/芯片文档，做一次嵌套实测 |
| 只设置子优先级 | 同抢占级仍不能相互打断 | 先设计抢占层，再设计同层顺序 |
| 在多个模块重复设置分组 | 后设置者可能改变整个系统的解释方式 | 统一初始化位置，其他模块只申请 IRQ 参数 |
| 在 ISR 中打印和延时 | 阻塞其他中断，放大丢数据 | 记录事件，退出后再输出 |
| 看到回调就认为中断链路完整 | 可能是旧标志、错误 IRQ 或未清标志 | 从触发源、标志、IRQ 入口、HAL 和回调逐层验收 |
