# STM32 串口接收：中断搬运、环形缓冲与命令解析

## 适用场景

当串口输入从“收一个字节并回显”升级为“接收一行命令、保留突发数据、交给主循环处理”时，可以把接收链拆成三段：

1. USART 外设把收到的字节放入数据寄存器，并产生接收事件。
2. 中断服务函数尽快把字节交给缓冲区。
3. 主循环按自己的节奏取字节、组帧、解析和执行。

这页适合文本命令或带明确帧边界的轻量协议。二进制协议、校验和、DMA 和高吞吐场景需要在这个结构上继续扩展，不能直接照搬文本解析。

## 先记住三条分工

| 位置 | 只负责什么 | 不应该做什么 |
| --- | --- | --- |
| USART 硬件 | 接收串行位流，形成一个字节并更新状态位 | 不负责理解命令含义 |
| 接收中断 | 读取数据寄存器，把字节放入接收缓冲 | 不做 `printf`、字符串解析、延时或复杂业务 |
| 主循环或低优先级任务 | 从缓冲取字节，识别帧，校验参数并执行 | 不等待“下一字节什么时候到” |

ST 的 STM32F1 参考手册说明，接收每个字节后会置位 `RXNE`；当下一个字节到达而前一个接收数据仍未及时处理时，会产生溢出条件并置位 `ORE`。因此，接收中断的第一目标是尽快取走硬件寄存器中的数据，缓冲区满和硬件 `ORE` 也应分别留下可观察的计数或状态。

## 一、先画出数据所有权

在写代码前先把读写者写下来：

| 数据 | 写入者 | 读取者 | 需要说明的边界 |
| --- | --- | --- | --- |
| USART 数据寄存器 | USART 硬件 | 接收中断 | 不及时读取可能出现 `ORE` |
| 环形缓冲槽位 | 接收中断 | 主循环 | 中断只推进写侧，主循环只推进读侧 |
| 当前行缓冲 | 主循环 | 主循环 | 必须给字符串结尾符留下空间 |
| 解析后的命令参数 | 主循环 | 业务模块 | 参数校验通过后才能执行 |

如果 `head`、`tail`、`count` 由不同上下文共同修改，必须单独说明谁修改哪个字段，以及读取和更新是否需要临界区。`volatile` 只能影响编译器对访问的处理，不能自动提供互斥、原子复合操作、队列不溢出保证或协议正确性。

### 补充：DR 读写与接收时限（STM32F103x8/xB）

先画出硬件路径：`引脚 → 接收移位寄存器 → RDR → 软件缓冲 → 主循环`。在本型号的普通单缓冲接收模型中，RDR 保存一份待取走的数据，不是可积累多字节的 FIFO；本段以 8N1 为例，9 位数据模式需另核对读取宽度。

| 程序访问 | 硬件含义 | 读码时应记录 |
| --- | --- | --- |
| 写 `USARTx->DR` | 交给发送数据寄存器 TDR | 发送方向；不能用一次写操作判断发送已完成 |
| 读 `USARTx->DR` | 从接收数据寄存器 RDR 取数据 | 接收方向；读取具有取数和标志处理的副作用 |

同一 DR 地址承担读、写两种角色，不等于软件在读回自己刚写入的发送数据。若上一份数据仍未取走，后续接收产生 ORE 时，原 RDR 数据保留，新接收数据可能丢失；清标志不能把丢失内容补回。依据见 [ST RM0008 的 USART 接收与数据寄存器说明（Keil 托管 Rev 9）](https://www.keil.com/dd/docs/datashts/st/stm32f10xxx.pdf)，实际使用应回到芯片当前手册及勘误。

普通接收中，`RXNEIE` 也与 ORE 的中断请求有关；DMA 模式还需核对 `DMAR`、`EIE` 等条件。不能把 ORE 写成“永不触发中断”。本型号清除 ORE 使用先读 `SR`、再读 `DR` 的序列，读到的数据如何保留以及标志如何交给上层，应统一放在当前 SPL/HAL 接收和错误路径中处理，避免应用层与驱动层重复读取 DR。以上寄存器规则只限本段所述型号，不直接迁移到其他系列。

### 先算可用时间，再选择轮询、中断或 DMA

保留来源的条件换算：115200、8N1、连续无间隙输入时，一帧共 10 位，帧间到达间隔约为 `10 / 115200 秒 = 86.8 微秒`。这个数字是帧长换算，不是本轮测量。

轮询是否可用，取决于**最坏服务延迟**能否赶上数据到达；还应考虑关中断、长任务、临界区和搬运本身的开销。不能只看主循环平均一圈多快，也不将轮询一概判为不可用。中断和 DMA 同样需要延迟、容量及错误恢复设计。

| 要填写的事实 | 用途 |
| --- | --- |
| 波特率、数据位、校验、停止位、最短帧间间隔 | 确定最密集的数据到达节奏 |
| 最大连续发送量 | 确定一次突发可能带来多少待处理数据 |
| 硬件取数的最坏延迟 | 评估硬件来不及交接的风险 |
| 软件缓冲可用容量、主循环最长不取数时段 | 评估缓冲满与丢弃策略 |
| ORE 事件、软件丢弃、行超长的分别记录方式 | 区分丢失发生在哪一层 |

软件队列只能保存已经搬入内存的数据；容量耗尽或长期消费速度不足时仍会丢弃。ORE 事件数也不等于精确丢失字节数。处理错误时，除记录事件，还要决定是否丢弃当前半帧、等待下一帧边界或请求重传，避免把缺字节命令继续当作完整命令执行。

## 二、接收中断只做最短路径

STM32F1 的 SPL 工程通常会在接收中断中检查 `RXNE`，再通过 `USART_ReceiveData()` 取出数据。下面只是结构示意，接口名、USART 实例和中断函数名要按芯片、启动文件和工程配置核对：

```c
void USART_IRQHandler(void)
{
    if (USART_GetITStatus(USARTx, USART_IT_RXNE) != RESET) {
        uint8_t byte = (uint8_t)USART_ReceiveData(USARTx);

        if (!rx_buffer_push(byte)) {
            rx_drop_count++;
        }
    }
}
```

上面的结构只示意正常 RXNE 取数，不包含完整 ORE、NE、FE、PE 错误处理；实际工程还需按当前芯片和库版本补齐错误路径与半帧恢复。

中断路径的动作顺序应保持简单：

1. 判断确实是接收事件。
2. 读取数据寄存器。
3. 尝试写入接收缓冲。
4. 缓冲满时按预先确定的策略计数或置错，不覆盖规则不能临时改变。
5. 尽快返回被打断的代码。

不要在这里等待一整行、调用 `printf`、执行 `sscanf`、操作显示屏或延时。中断执行越久，下一字节越可能来不及被取走；主循环也会被迫长时间暂停。

## 三、环形缓冲要先选满载策略

环形缓冲至少需要固定容量、读位置和写位置。常见实现有两种：

### 方案 A：维护元素数量

- `head` 指向下一次写入位置。
- `tail` 指向下一次读出位置。
- `count` 表示当前未读字节数。
- 写入成功后增加 `count`，读出成功后减少 `count`。
- `head` 和 `tail` 到容量末尾后回到 0。

优点是“空”和“满”都能直接表达；代价是 `count` 由读写两侧共同触碰，需要明确并发交接。

### 方案 B：保留一个空槽

- `head == tail` 表示空。
- 下一次推进 `head` 后等于 `tail` 时表示满。
- 实际可用容量比数组长度少一个槽位。

优点是只靠两个位置即可区分空满；代价是必须向读者说明“数组长度”和“可用容量”不是同一个数。

无论选哪种方案，都要在文档中写清缓冲满时的行为：

| 策略 | 保留什么 | 适用提醒 |
| --- | --- | --- |
| 丢弃新字节 | 保留已有数据 | 适合不希望破坏半帧的文本命令；必须累计丢弃数 |
| 覆盖最旧字节 | 保留最新数据 | 适合只关心最新状态；可能破坏一条正在组装的命令 |
| 拒绝并报告 | 保留队列状态并通知上层 | 需要协议或发送端支持重试，UART 本身不会替你完成回压 |

“数据少了”必须能够定位来源。至少区分硬件 `ORE`、环形缓冲满丢弃和行缓冲超长三类计数，不能只在最后输出一个含义不清的 `DROP`。

## 四、主循环负责组帧，不负责等数据

接收字节只是字节流。主循环必须先选一种帧边界：

- 换行结束：适合文本命令，约定 `\n` 或 `\r\n`。
- 固定长度：适合长度稳定的二进制帧。
- 长度字段：先读帧头和长度，再收够指定数量。
- 空闲线或超时：适合没有固定结束符的传输，但必须定义计时器和半帧处理。

以换行文本为例，主循环可以采用以下结构：

```c
void service_rx(void)
{
    uint8_t byte;

    while (rx_buffer_pop(&byte)) {
        if (byte == '\n') {
            line[line_length] = '\0';
            dispatch_line(line);
            line_length = 0;
        } else if (line_length + 1U < LINE_CAPACITY) {
            line[line_length++] = (char)byte;
        } else {
            line_drop_count++;
        }
    }
}
```

这里有两个容易混淆的容量：环形缓冲保存的是“原始字节”，行缓冲保存的是“准备交给 C 字符串函数的字符”。后者必须额外留出一个 `\0` 的位置。收到 `\r\n` 时，要提前决定是删除 `\r`，还是把它当作普通字符保留，不能让不同命令得到不同规则。

主循环应该在缓冲暂时为空时立即返回，继续处理按键、定时任务和其他状态。否则串口另一端可以通过“迟迟不发送换行”把整个系统卡在等待里。

## 五、解析前先保证字符串条件

### 无参数命令

```c
if (strcmp(line, "LED ON") == 0) {
    led_on();
}
```

`strcmp` 接收的是两个指针，但比较的是两个以 `\0` 结尾的字符串内容；相等时返回 0。调用前必须确认 `line` 已经正确结尾，并且没有把仍在缓冲中的非字符串字节直接交给字符串函数。

### 带参数命令

```c
int level;

if (sscanf(line, "LED %d", &level) == 1 && level >= 0 && level <= 100) {
    led_set_level(level);
}
```

解析函数的返回值表示成功赋值的数量，不能只看目标变量当前内容。参数范围也要单独检查；“成功读出了一个整数”不代表这个整数适合直接写入硬件寄存器。

对于资源紧张、输入不受信任或协议要求严格的设备，可以把解析器改成逐字符状态机，显式处理命令名、分隔符、数字范围、结束符和错误恢复。文本方便阅读，状态机更容易限制输入成本；选择取决于协议约束，不要把 `sscanf` 当成通用协议解析器。

## 六、按这个顺序落地

1. **先定义帧**：写清结束符、最大长度、空行、`\r\n`、非法字符和半帧超时策略。
2. **再接收单字节**：只确认 USART 实例、GPIO 复用、波特率、接收中断和 NVIC 路径一致。
3. **加入环形缓冲**：明确容量、空满判据、满载策略和丢弃计数。
4. **加入主循环取数**：缓冲为空就返回，不能用死循环等下一字节。
5. **加入组帧**：遇到帧边界才把字节序列转成待解析对象。
6. **加入解析**：先判断函数返回值，再检查参数范围和命令权限。
7. **加入可观察状态**：保留接收字节数、硬件错误、缓冲丢弃、行超长和未知命令计数。
8. **最后接业务动作**：让解析层输出结构化命令，业务层决定是否改变 LED、PWM 或其他外设。

每一步只引入一个新变量或新责任。这样出现“无输出”“命令偶尔失效”或“系统卡住”时，可以判断问题属于硬件接收、队列交接、组帧、解析还是业务执行。

## 不适用与扩展

- 二进制数据可能包含 `0x00`，不能直接用 C 字符串函数；应使用长度和状态机。
- 高速连续数据可能让“每字节一次中断”成为瓶颈，可评估 DMA 循环缓冲或空闲线检测。
- 命令会改变关键外设时，应增加权限、校验和错误恢复，不要把串口文本当作天然可信输入。
- 本页不替代芯片参考手册、板卡原理图和当前工程配置。USART 实例、引脚复用、寄存器清标志顺序和 SPL/HAL 函数必须按实际器件资料核对。
