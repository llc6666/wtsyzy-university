# 阶段复盘与成果回流

## 何时用

项目结束、学期结束、一次试做停止，或一个月过去却说不清做成什么时使用。复盘的目的不是写感想，而是决定保留、修正或停止哪种做法。

## 输入

- 原项目卡或决策卡。
- 实际产物、时间记录、反馈和关键版本。
- 30 分钟不被打断的时间。

## 步骤

### 1. 先对照原目标

不要先写“收获很大”。先把原来的目标、范围、验收标准抄到左栏，再在右栏写实际结果。原记录缺失时，明确写“无法比较”，这本身就是流程问题。

| 项目 | 原计划 | 实际结果 | 偏差 | 证据 |
| --- | --- | --- | --- | --- |
| 交付物 |  |  |  | 链接/文件 |
| 时间成本 |  |  |  | 日历/日志 |
| 外部反馈 |  |  |  | 评语/数据 |
| 风险判断 |  |  |  | 事件记录 |

### 2. 找一个可改变的因果点

只选择能被下次行动改变的原因。"我不够自律"没有操作性；"第一周没有做最小版本，直到截止日前才发现环境无法运行"能改为“第 3 天必须完成可运行样例”。

### 3. 把内容分到四个去处

| 内容 | 去处 | 判断标准 |
| --- | --- | --- |
| 原始数据、反馈、版本 | Sources 或 Outputs | 后续需要复查原样证据 |
| 已验证且可复用的方法 | Wiki | 有来源、条件、反例 |
| 仍不确定的解释 | Research | 写出假设和下一步验证 |
| 下次要做的具体动作 | 决策/项目卡 | 有时间和负责人 |

### 4. 写不超过 10 行的复盘结论

固定使用：`结果`、`证据`、`原因`、`下次动作`、`不适用场景`。一条复盘只提炼一个方法，超过一个就拆分。

```markdown
## 复盘结论
- 结果：
- 证据：
- 原因：
- 下次动作：
- 不适用场景：
- 已回流页面：
```

## 交付物

- 1 张计划与实际对照表。
- 1 条可改变原因。
- 至少 1 个回流链接，或明确“没有稳定结论，不晋升”。

## 验收

- 结果可由文件、数据或外部反馈定位。
- 下次动作具体到行为和时间，不是“继续努力”。
- 从项目页能找到产物和复盘；从 Wiki 能回到证据。
- 失败经验没有被包装成普遍规律。

## 常见失败与修正

- 复盘写成情绪日记：保留情绪，但另补计划与实际对照表。
- 只总结成功：至少写一个成本超预期或假设失效点。
- 所有经验都晋升 Wiki：无法跨情境复用的内容留在项目页。
- 每次复盘都重新设计系统：只改一个下一周期能验证的流程点。
