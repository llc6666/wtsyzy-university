# Android 单文件 C++ 工具：架构边界与验收门禁

## 这页解决什么问题

在 Android 平板上做一个能编辑、编译和运行单文件 C++ 的工具时，界面能打开不等于功能完成，代码能编译也不等于运行安全。解决方法是先锁定最小产品边界，再把文件、编译、运行和验收拆成独立门禁。

## 1. 先锁定最小范围

第一版只承诺一个 `.cpp` 文件、少量明确的 C++ 标准、打开/保存、编译、标准输入输出和可停止运行。代码补全、调试器、多文件工程、CMake、第三方依赖和网络功能应当单独立项。

| 功能 | 第一版边界 | 验收问题 |
| --- | --- | --- |
| 编辑 | 原生文本编辑器，优先支持实体键盘 | 输入、撤销、查找和跳转是否稳定 |
| 文件 | 通过 Storage Access Framework 打开和保存用户文件 | 权限是否来自用户选择，重启后是否仍能访问 |
| 草稿 | 应用私有目录保存工作副本和草稿 | 强制关闭后能否恢复，是否区分正式保存 |
| 编译 | 固定 ABI 的内置 Clang，版本和摘要可追踪 | 工具链来源、版本和校验是否完整 |
| 运行 | 独立隔离服务执行用户代码 | 无限循环、错误输出和停止动作是否可控 |
| 状态 | 编译结果绑定源代码摘要、标准和工具链版本 | 修改一个字符后是否禁止运行旧产物 |

## 2. 文件边界：用户文件与应用内部数据分开

用户主动选择的源文件属于共享文档；编译工作副本、自动草稿和编译产物只服务于应用自身。两类数据不能混在一个目录，也不能用“申请整个存储权限”代替文件访问设计。

推荐流程：

1. 使用 `ACTION_OPEN_DOCUMENT` 读取用户选中的 `.cpp`。
2. 使用 `ACTION_CREATE_DOCUMENT` 让用户选择正式保存位置。
3. 把工作副本、草稿、诊断信息和编译产物存到应用私有目录。
4. 记录 URI 权限和源文件摘要，重启后重新打开时验证内容是否变化。
5. 正式保存成功后清除“未保存”标记；自动草稿恢复时明确提示尚未正式写回用户文件。

Android 官方文档将应用私有存储和共享文档区分开：应用私有数据适合只由本应用访问的内容，Storage Access Framework 适合由用户选择位置后访问文档。

## 3. 运行边界：UI 不直接执行用户代码

建议拆成四层：

```text
Compose/UI
  → ViewModel / 状态机
    → 文件与编译协调层
      → 隔离运行服务
```

- UI 只展示状态、输入动作和输出，不持有编译器细节。
- 状态机明确“编辑中 → 编译中 → 编译成功/失败 → 可运行/不可运行 → 运行中 → 已停止/异常”的转移条件。
- 文件与编译层负责快照、临时目录、编译命令、退出码和诊断结果。
- 用户代码放在声明 `android:isolatedProcess="true"` 的服务中执行，主进程通过受控的 Service API 接收状态和输出。

`isolatedProcess` 只能减少权限和主进程被直接影响的风险，不能替代超时、资源限制、输出上限、进程回收和输入校验。隔离服务仍必须经过真机测试，不能只检查 Manifest 文本。

## 4. 防止运行旧产物

每次编译生成一个运行资格记录：

```text
source_sha256
language_standard
toolchain_version
compile_exit_code
artifact_path
```

点击“运行”前重新计算当前源代码摘要，并比较语言标准与工具链版本。任一项不同，就禁用运行，要求重新编译。

## 5. 工具链不能靠“能用”放行

内置 Clang、链接器、C++ 标准库、Android NDK sysroot 和传递依赖需要分别记录来源、版本、提交号、许可证、文件清单和 SHA-256。构建脚本要拒绝版本、ABI 或包名不匹配的输入，不应从未知软件或现成二进制包静默替换。

工具链 bundle 还要满足：

- 不含宿主机绝对路径；
- ZIP 内没有 `..`、重复条目和未登记文件；
- 每个二进制和许可证文件都在 manifest 中；
- APK 内能读到第三方许可证；
- 真机首次启动不依赖网络或额外安装 Termux。

## 6. 测试分层和门禁

不要把本地 JVM 单元测试、Android 仪器测试和真机验收混成一个“测试通过”。

| 层级 | 适合验证 | 不能证明 |
| --- | --- | --- |
| JVM 单元测试 | 编辑器状态、解析、摘要、状态机和纯 Kotlin 逻辑 | Android 文件权限、隔离进程和真实 UI |
| Android 仪器测试 | Activity、Service、SAF、Manifest 和设备 API 交互 | 所有设备型号、离线体积和性能 |
| 真机验收 | 安装、键盘、横屏、编译、运行、停止、断网和恢复 | 其他未测设备和未覆盖的异常路径 |

第一批测试程序应故意包含正常输出、标准输入、语法错误、无限循环、C++17/20/23 各一个特性。每个测试保存输入、预期输出、退出码和日志。

## 7. 可执行验收顺序

1. `:app:testDebugUnitTest`：先验证纯逻辑。
2. `:app:lintDebug`：处理静态检查。
3. `:app:assembleDebug`：确认 APK 能生成并记录大小、ABI 和哈希。
4. `:app:connectedDebugAndroidTest`：在真实设备执行仪器测试。
5. 依次验证打开、保存、草稿恢复、编译、错误定位、运行、停止和断网。
6. 关闭应用并重新打开，确认源文件和草稿边界仍然成立。

每个门禁都要记录命令、退出码、报告路径、设备信息和 Git 提交号。命令写在文档里不等于执行过；没有实际读回结果的项目只能标记为“未验收”。

## 8. 失败模式

| 失败模式 | 修正动作 |
| --- | --- |
| UI 能显示但按钮没有真实闭环 | 给每个按钮绑定状态转移和可读的失败结果 |
| 把编译器放在主进程 | 移到隔离运行边界，并增加停止、超时和输出限制 |
| 用户文件、草稿和产物混在一起 | 用 SAF 处理用户文件，用应用私有目录处理内部数据 |
| 修改代码后仍可运行 | 运行前重新比较源代码、标准和工具链摘要 |
| 只在电脑上测试 | 增加仪器测试和真机门禁，保存原始报告 |
| 直接打包未知工具链 | 固定来源、版本、ABI、许可证和哈希，构建后验证 bundle |

## 发布判断

项目介绍可以公开架构、边界、测试设计和当前未完成项；不能把“代码已写”“测试类已写”写成“APK 可用”“真机通过”或“离线运行已证明”。当前项目记录中的工具链构建、APK 构建和真机 G1/G2 门禁均保持未验收状态。
