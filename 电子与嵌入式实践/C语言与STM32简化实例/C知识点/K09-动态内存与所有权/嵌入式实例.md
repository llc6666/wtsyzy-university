# K09 嵌入式实例

## 一、PC 侧：已验证

文件：[malloc-ownership-demo.c](malloc-ownership-demo.c)

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic malloc-ownership-demo.c -o malloc-ownership-demo.exe
```

实测输出（gcc 16.2.0，2026-10-01）：

```text
1) malloc 未初始化，内容不确定；calloc 清零：0 0 0 0 0
2) 已释放并把指针置 NULL；此时再 free 一次仍是错的，但判空可以防住误用
   a == NULL，不会被误用
3) 链表内容：4 1 3
   销毁后 head = NULL
4) 静态/固定数组：大小=64，编译期确定，不会失败也不会碎片
5) 小结：PC 上可以随意 malloc；裸机上更倾向编译期定死的数组与内存池
```

第 3 步的 `销毁后 head = NULL` 是所有权交接的完整示范：销毁函数通过二级指针把调用方的指针也清空。

## 二、嵌入式对照：三种分配方式

| 方式 | 什么时候失败 | 碎片 | 耗时 | 典型用途 |
| --- | --- | --- | --- | --- |
| 栈（局部变量） | 栈溢出 | 无 | 极快 | 函数内的临时变量 |
| 静态（全局/`static`） | 编译期确定，不会失败 | 无 | 无 | 缓冲区、状态、对象池 |
| 堆（`malloc`） | **运行时可能失败** | 有 | 不定 | 通用程序；裸机上慎用 |

STM32F103 的 RAM 通常只有 20 KB，堆和栈共用这块空间，一次 `malloc` 失败就可能让后续所有分配都失败。

## 三、内存池：固定大小块的分配器

裸机上更常见的做法是自己管一块静态数组：

```c
#define POOL_BLOCKS 16
#define BLOCK_SIZE  32

static uint8_t pool_mem[POOL_BLOCKS][BLOCK_SIZE];
static bool    pool_used[POOL_BLOCKS];

void *pool_alloc(void)
{
    for (size_t i = 0; i < POOL_BLOCKS; ++i) {
        if (!pool_used[i]) {
            pool_used[i] = true;
            return pool_mem[i];
        }
    }
    return NULL;           /* 池满了，明确返回失败 */
}

void pool_free(void *p)
{
    for (size_t i = 0; i < POOL_BLOCKS; ++i) {
        if (pool_mem[i] == p) { pool_used[i] = false; return; }
    }
}
```

（示意写法，未上板验证。）

优点：分配时间固定、**不会产生碎片**、失败行为可预测。代价：块大小固定，不够灵活。

## 四、中断里绝不能 malloc

两条理由：

1. `malloc` 通常**不可重入**：主流程正改到一半的堆管理结构，被中断打断后再进去改一次，结构就坏了
2. 耗时不确定，会拖长中断响应时间

中断里要做数据传递，用**环形缓冲**（K12）或「置标志 + 主循环处理」（K10）。

## 五、把本知识点带回 PC 的做法

写链表、树这类结构时，先在 PC 上用 ASAN 跑一遍，确认零泄漏：

```bash
gcc -std=c17 -Wall -Wextra -Wpedantic -fsanitize=address -g demo.c -o demo.exe
```

ASAN 会明确报出「哪个地址在哪一行分配、从未释放」。把这套检查养成习惯，比在 MCU 上靠现象猜内存问题省事得多。
