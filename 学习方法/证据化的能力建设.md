# 证据化的能力建设

## 何时用

准备把“学过”“参加过”“会一点”变成可复查证据，或发现自己学了很久却无法独立完成任务时使用。

## 输入

- 一项待证明能力。
- 7 至 14 天可投入时间。
- 一个外部反馈源：测试、教师、同学、用户、评审或公开标准。

## 步骤

### 1. 把能力改写成任务

“学习 C++”太大；“在 10 天内实现一个可运行的栈，并通过 12 个边界测试”可执行。任务要同时包含场景、产物和验收。

### 2. 开始前写证据计划

| 项目 | 填写内容 |
| --- | --- |
| 能力 | 要证明的具体动作 |
| 真实任务 | 在什么约束下完成 |
| 产物 | 代码、报告、作品、演示或记录 |
| 验收 | 测试、评分规则或他人反馈 |
| 个人贡献 | 自己独立完成的部分 |
| 截止日 | 最晚交付时间 |

### 3. 按三段推进

- 第 1 至 2 天：完成最小可运行版本，立刻发现环境和基础缺口。
- 中段：做 3 至 5 次独立练习，保留失败样例和修改记录。
- 最后 2 天：按验收标准测试，向外部对象获取一次反馈，写 10 行以内复盘。

### 4. 整理成果包

成果包至少含 `README/任务说明`、可打开的产物、验证记录、个人贡献和下一步改进。团队成果必须清楚区分个人部分，不能用团队名称代替能力证据。

## 交付物

一个能独立打开的成果包，以及一份任务、验证与反馈的记录。

## 验收

- 陌生人按 README 能打开、运行或理解产物。
- 至少有一条独立于自我评价的反馈或测试结果。
- 保留了一个失败样例、修改原因或边界条件。
- 能准确说清个人贡献和未解决缺口。

## 常见失败与修正

- 只看教程：第 2 天前必须写出最小版本。
- 为了作品凑复杂功能：先补测试、说明和可复现步骤。
- 把一次成功当成熟能力：换一个输入或约束再做一次。
- 团队项目贡献模糊：每周记录自己负责的文件、决策和验证。
