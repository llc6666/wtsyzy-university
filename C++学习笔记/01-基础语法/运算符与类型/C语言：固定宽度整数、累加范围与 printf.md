# C 语言：固定宽度整数、累加范围与 `printf`

## 适用场景

当数据来自硬件寄存器、通信协议、文件格式或二进制缓冲区，并且位数本身有含义时，先选择固定宽度整数类型，再单独设计计算时的累加类型。

例如 12 位 ADC 读数可放进 `uint16_t`，但连续多次读数的和可能超过 16 位范围。变量能存下单个元素，不代表它能存下计算结果。

## 你需要准备什么

- 支持 C17 的编译器。
- `<stdint.h>`：声明固定宽度整数类型。
- `<inttypes.h>`：提供与这些类型配套的输出格式宏。
- 一张范围表：记录单个值范围、元素数量、理论最大和，以及目标类型上限。

不要用“我的电脑上 `int` 是 4 字节”代替范围设计。`int` 和 `long` 的宽度会随目标平台和 ABI 变化；接口需要固定宽度时，先写出需要的位数。

## 第一步：区分存储类型与计算类型

下表中的“位”描述目标接口要求，不是推荐随意把所有变量都写成同一种类型。

| 对象 | 合理类型 | 为什么 |
| --- | --- | --- |
| 0 到 4095 的 ADC 原始值 | `uint16_t` | 能明确表达无符号、至少容纳 12 位数据 |
| 四次最大 60000 的和 | `uint32_t` | 最大和为 `4 × 60000 = 240000`，超过 16 位无符号最大值 65535 |
| 数组下标与字节数量 | `size_t` | 与对象大小和数组索引的接口一致 |
| 可能为负的差值 | 根据范围选择 `int32_t` 等有符号类型 | 不能把负数状态塞进无符号变量 |

计算前先算上界：

```text
最大累计值 = 单个元素最大值 × 最多累计次数
```

再选择能覆盖该上界的类型。若上界接近类型极限，还要给后续乘法、偏移或中间结果留出余量。

## 第二步：用精确格式宏打印

`uint16_t` 和 `uint32_t` 是 typedef。它们在不同平台上可能映射到不同基础类型，手写 `%u`、`%lu` 等格式符会把输出正确性绑死在当前平台的实现细节上。

使用 `<inttypes.h>` 中的 `PRIu16`、`PRIu32`：

```c
printf("total = %" PRIu32 "\n", total);
```

编译时开启 `-Wformat`。GCC 会检查 `printf` 格式字符串与实参类型是否匹配；警告不能靠强制转换长期掩盖，先确认变量的真实类型与接口要求。

## 最小可验证示例

配套程序：[C语言固定宽度整数与累加.c](../../代码示例/C语言固定宽度整数与累加.c)。它故意用四个 `60000` 相加：16 位累计变量发生模回绕，32 位累计变量保留正确总和。

```c
#include <inttypes.h>
#include <stdint.h>
#include <stdio.h>

int main(void) {
    const uint16_t samples[] = {60000u, 60000u, 60000u, 60000u};
    uint16_t narrow_total = 0u;
    uint32_t wide_total = 0u;

    for (size_t i = 0; i < sizeof samples / sizeof samples[0]; ++i) {
        narrow_total = (uint16_t)(narrow_total + samples[i]);
        wide_total += samples[i];
    }

    printf("16-bit total = %" PRIu16 "\n", narrow_total);
    printf("32-bit total = %" PRIu32 "\n", wide_total);
    return 0;
}
```

运行后应输出：

```text
16-bit total = 43392
32-bit total = 240000
```

第一行不是正确总和。它表示结果被写回 16 位无符号对象后按该类型范围回绕。第二行才满足本例的累计范围。

## 如何验收

在代码示例目录中执行：

```powershell
gcc -std=c17 -Wall -Wextra -Wpedantic -Wformat "C语言固定宽度整数与累加.c" -o fixed-width.exe
.\fixed-width.exe
```

检查四项：

1. 编译没有警告或错误。
2. 16 位结果为 `43392`，用于确认示例确实覆盖了回绕风险。
3. 32 位结果为 `240000`，与 `4 × 60000` 一致。
4. 把数组改为一个 `60000` 后，两种累计结果都应为 `60000`；这说明问题来自累计范围，而非单个样本的存储。

本页配套代码已于 2026-09-17 使用 `gcc -std=c17 -Wall -Wextra -Wpedantic -Wformat` 编译，并验证了四元素累计与单元素边界。更换目标编译器、ABI 或类型后，应重新编译和记录输出。

## 常见错误与修正

| 错误 | 后果 | 修正 |
| --- | --- | --- |
| 用元素类型直接累计 | 总和在赋值时回绕 | 为累计值单独选择覆盖上界的更宽类型 |
| 只看当前平台 `sizeof(int)` | 换目标平台后范围假设失效 | 接口数据使用 `<stdint.h>` 类型，并实际打印/测试大小 |
| 把有符号差值放进 `uint16_t` | 负值变成很大的正数 | 先明确值域是否允许负数 |
| `printf` 格式符靠猜 | 输出错位或触发未定义行为风险 | 使用 `PRIu16`、`PRIu32` 等格式宏并开启格式检查 |
| 用强制类型转换压掉警告 | 真实范围问题被隐藏 | 回到变量类型、范围表和接口定义 |
| 只测试普通读数 | 极值累计错误到现场才出现 | 至少测试单个最大值、多个最大值和接近上界的次数 |

## 什么时候不适用

- 若协议或寄存器定义要求的是位字段、字节序或原子访问，固定宽度类型只是第一步，还要按芯片手册和通信协议处理布局与并发。
- 若累计次数或中间乘法可超过 32 位，不能继续沿用 `uint32_t`，需要重新计算上界。
- 若目标平台没有提供某个精确宽度类型，`uint16_t` 等名称可能不可用；应检查目标工具链头文件和接口约束，不能静默换成看似接近的类型。

编译器、C 库和目标 ABI 可能不同。涉及外设寄存器、协议报文和跨平台二进制文件时，以当前芯片手册、协议文档和实际目标编译结果为准。
