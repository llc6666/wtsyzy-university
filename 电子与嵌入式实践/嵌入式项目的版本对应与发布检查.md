# 嵌入式项目的版本对应与发布检查

> 目标：确保一块实际硬件、一份固件、一张原理图和一份测试结果可以互相对应。它用于个人项目和小团队协作，不替代企业的质量体系或量产流程。

## 何时使用

- 项目有多个 PCB 版本、多个开发板或多份固件时。
- 准备交接、比赛演示、开源发布或返修时。
- 出现“这个 hex 是给哪块板的”“为什么新板跑旧代码”一类问题时。

## 输入

1. 硬件标识：板卡名称、版本、原理图、PCB、物料清单或采购记录。
2. 固件仓库的提交号、构建方式、编译器和依赖版本。
3. 测试用例、实际测量结果和已知问题。
4. 公开发布范围与授权状态。

## 操作步骤

### 1. 建立版本对应表

| 硬件 ID | 原理图 / PCB 版本 | 固件提交 | 工具链 | 构建产物 | 已测功能 | 结果 | 状态 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| `board-a-r1` | 链接或标签 | Git 短提交号 | 编译器与版本 | `.elf/.bin` 的生成时间与哈希 | 串口、PWM 等 | 通过/失败 | 可演示/待修复 |

每次烧录都先在表中登记“硬件 ID + 固件提交”。二者缺一个，就不开始集成测试。

### 2. 让源码、配置和产物可追溯

```powershell
git status
git diff
git add <本次实际修改的文件>
git commit -m "feat: verify uart echo on board-a-r1"
git rev-parse --short HEAD
```

提交前确认生成目录、调试日志、私钥、账号配置、下载工具安装包和未知二进制没有被加入版本控制。Git 的基本追踪、暂存与提交方式见[官方文档](https://git-scm.com/book/en/v2/Git-Basics-Getting-a-Git-Repository)。

### 3. 按版本运行最小测试集

测试用例先写输入和期望，再记录实际结果。示例：

| 用例 | 输入 | 期望 | 实际证据 | 结果 |
| --- | --- | --- | --- | --- |
| 冷启动 | 断电 10 秒后上电 | 串口在 2 秒内输出版本标识 | 日志文件 | 通过/失败 |
| UART 回显 | 连续发送 20 个字符 | 全部原样返回 | 原始串口记录 | 通过/失败 |
| PWM | 固定配置 | 测得频率与脉宽在目标误差内 | 仪器读数 | 通过/失败 |

### 4. 发布前分层检查

1. **代码**：从空构建目录重新构建，记录命令和工具版本。
2. **硬件**：确认发布的原理图、PCB、BOM 与测试板版本一致。
3. **资料**：只发布自己有权公开的内容；第三方库、图片、数据手册和工程包保留许可证或链接。
4. **隐私与安全**：移除成员联系方式、云端令牌、Wi-Fi 密码、私有地址、调试密钥和设备序列号。
5. **说明**：写明支持的硬件版本、构建步骤、烧录方式、已知限制和复现测试。

## 交付物

- 一张硬件、固件、测试三方对应表。
- 可重建的源码与配置。
- 一份最小测试表和已知问题列表。
- 对外发布时的一份范围和许可证检查记录。

## 验收

- 任一演示或发布固件都能追溯到唯一的硬件 ID 与 Git 提交。
- 测试表包含失败项，不能只保存通过截图。
- 另一位使用同版本硬件的人能依照文档构建、烧录并完成最小测试。
- 公开仓库不包含无授权资料、密钥、成员信息和私有工程路径。

## 常见失败与修正

- **硬件改了但没改版本号**：在板上、原理图文件名和版本表中同时更新硬件 ID。
- **上传 `final_final2.hex`**：用提交号、硬件 ID 和构建日期命名，并保留源码构建入口。
- **只测当前手中的板子**：测试记录要写板卡版本；跨版本复用前必须重新验证。
- **把所有内容直接推到公开仓库**：先做脱敏和授权审查，再决定是发布源码、摘要、链接还是不发布。

## 边界

Git 可以追踪文本和文件版本，不能证明硬件已被正确焊接或电气设计安全；关键电气结论仍要靠测量和设计审查。公开发布前还应遵守器件、软件、第三方代码和媒体资源的许可证。
